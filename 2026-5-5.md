### Solution Decision
After analyzing the impact of fully changing the Case/Subcase data model, the chosen solution is to introduce a new parent object called `Incident` instead of moving all operational and classification features from `Case` to `Subcase`.

The original clean modeling solution would require moving many fields such as:

- Domain
- Category
- SubCategory
- Classification
- Severity
- Stage
- Target Department / Section

from the `Case` level to the `Subcase` level.

However, this would cause a very large system-wide impact because the current backend architecture, APIs, reporting services, workflow logic, dashboard queries, endpoints, and frontend pages are heavily dependent on the current meaning of the `Case` object.

A full remodeling would require rewriting and adapting:

- API request/response objects
- Endpoints
- Backend services
- Reporting queries
- Dashboard aggregations
- Workflow logic
- Frontend pages
- Table views
- Filtering logic
- Export services

This creates a high regression risk late in the project lifecycle.

#### Chosen Transitional Solution

Instead of fully replacing the existing model, a new parent table called `APP_Incident` will be introduced.

The new architecture becomes:

```
Incident
    -> Cases
        -> Existing Subcase logic remains mostly unchanged
```

The `Incident` object stores the common/shared information between all related operational cases, including:

- Patient
- Doctor
- Worker
- Feedback Intent Type
- General complaint information

Each `Case` becomes an operational item linked to exactly one target department/section and contains its own classification and workflow data.

#### Database Changes

The following changes will be made:

1. Create new table:

```
APP_Incident
```

2. Add foreign key relation:

```
APP_IncidentCase.incident_id
    -> APP_Incident.incident_id
```

The existing `Case` and `Subcase` tables remain mostly intact to preserve compatibility with the current backend and reporting architecture.

#### Backend and UI Impact

The Insert Record page will be redesigned so that:

- The top section creates the shared `Incident` information.
- The user can create multiple `Cases` under the same `Incident`.
- Each `Case` will target only one department/section.
- Multiple case tabs can be dynamically added in the UI.

The system therefore transitions from:

```
One Case -> Multiple Subcases
```

to:

```
One Incident -> Multiple Operational Cases
```

while preserving most of the existing backend structure and workflow implementation.

#### Purpose of This Decision

The purpose of this solution is to support the new business workflow requirements while minimizing destructive changes to the current system architecture.

This is a transitional compatibility-oriented solution intended to:

- Reduce implementation risk
- Preserve existing services and reports
- Avoid a large-scale backend rewrite
- Minimize regression issues
- Allow gradual architectural evolution
- Deliver the required functionality safely
