	## Section A: Data Needs
	
	### A.1 Record Core Data (Text Fields)
	
	| Field              | Type | Required | Description                                    |
	| ------------------ | ---- | -------- | ---------------------------------------------- |
	| `complaint_text`   | Text | ✅ Yes    | Full complaint/incident description            |
	| `immediate_action` | Text | ❌ No     | Immediate actions taken at time of incident    |
	| `taken_action`     | Text | ❌ No     | Follow-up actions taken after initial response |
	
	---
	
	### A.2 Record Metadata
	
	|Field|Type|Required|Description|
	|---|---|---|---|
	|`feedback_received_date`|ISO Date|✅ Yes|Date the feedback/complaint was received|
	|`issuing_department_id`|Integer|❌ No|ID of department issuing the report|
	|`target_department_ids`|Array of Integers|❌ No|IDs of departments responsible for resolution|
	|`source_id`|Integer|❌ No|ID of feedback source (Phone, Email, etc.)|
	|`in_out`|Enum|❌ No|`"IN"` (inpatient) or `"OUT"` (outpatient)|
	|`worker_type`|String/Enum|❌ No|Worker type involved (Doctor, Nurse, Clerk, etc.)|
	
	**Note**: Code shows `target_department_ids` as array but payload uses singular `target_department_id`. Need clarification.
	
	---
	
	### A.3 Entity / Person Data (NER-Assisted)
	
	|Field|Type|Required|Description|
	|---|---|---|---|
	|`patient_name`|String|❌ No|Patient name (from NER or manual entry)|
	|`doctor_name`|String|❌ No|Doctor name (from NER or manual entry)|
	
	**Note**: These fields can be auto-populated by NER but are editable by user.
	
	---
	
	### A.4 Classification and Taxonomy (ID-Based)
	
	|Field|Type|Required|Description|
	|---|---|---|---|
	|`domain_id`|Integer|✅ Yes|Problem domain ID (e.g., Clinical, Management, Relational)|
	|`category_id`|Integer|✅ Yes|Category ID within selected domain|
	|`subcategory_id`|Integer|❌ No|Subcategory ID (if applicable)|
	|`classification_id`|Integer|❌ No|Final classification ID (most specific level)|
	
	**Note**: These form a hierarchical taxonomy. Domain must be selected first, then category, then optional subcategory/classification.
	
	---
	
	### A.5 Severity and Impact Assessment (ID-Based)
	
	|Field|Type|Required|Description|
	|---|---|---|---|
	|`severity_id`|Integer|✅ Yes|Severity level ID (Low, Medium, High)|
	|`stage_id`|Integer|❌ No|Care stage ID (Admission, Care, Discharge, etc.)|
	|`harm_id`|Integer|❌ No|Harm level ID (No Harm, Minor, Major, etc.)|
	|`improvement_type`|Integer|❌ No|Whether improvement opportunity exists (0 = No, 1 = Yes)|
	
	---
	
	### A.6 System-Assigned Fields (Not in Form)
	
	|Field|Type|Description|Assignment|
	|---|---|---|---|
	|`record_id`|String/Integer|Unique record identifier|Backend assigns on creation|
	|`status_id`|Integer|Initial status|Hardcoded to `3` ("In Progress")|
	|`created_at`|ISO DateTime|Creation timestamp|Backend assigns|
	|`created_by`|String|User who created the record|Backend assigns from auth context|

	## Section B: API Endpoints
	
	### B.1 Create New Record Endpoint
	
	**Purpose**: Submit a new incident/feedback record to the database
	
	```
	POST /api/records/add
	```
	
	**Request Headers**:
	
	```
	Content-Type: application/json
	Authorization: Bearer <token>
	```
	
	**Request Body**:
	
	```
	{
	  "complaint_text": "تأخر كبير في تشخيص الحالة الطارئة مما أدى إلى تفاقم الحالة",
	  "immediate_action": "تم توفير الرعاية الفورية وتحويل المريض للوحدة المختصة",
	  "taken_action": "تم متابعة الحالة وتحديث البروتوكول",
	  "feedback_received_date": "2024-12-15",
	  "issuing_department_id": 5,
	  "target_department_id": 8,
	  "source_id": 2,
	  "in_out": "IN",
	  "worker_type": "Doctor",
	  "patient_name": "أحمد محمد علي",
	  "doctor_name": "د. خالد حسن",
	  "domain_id": 1,
	  "category_id": 12,
	  "subcategory_id": 45,
	  "classification_id": 102,
	  "severity_id": 2,
	  "stage_id": 1,
	  "harm_id": 2,
	  "improvement_type": 1
	}
	```
	
	**Field Requirements**:
	
	- **Required**: `complaint_text`, `feedback_received_date`, `domain_id`, `category_id`, `severity_id`
	- **Optional**: All other fields
	
	**Response Structure** (Success):
	
	```
	{
	  "success": true,
	  "message": "Record created successfully",
	  "record_id": "REC-2024-0156",
	  "id": 156,
	  "status_id": 3,
	  "created_at": "2024-12-17T15:30:00Z"
	}
	```
	
	**Response Structure** (Validation Error):
	
	```
	{
	  "success": false,
	  "error": "VALIDATION_ERROR",
	  "message": "Complaint text is required",
	  "field": "complaint_text"
	}
	```
	
	**Response Structure** (Invalid Reference):
	
	```
	{
	  "success": false,
	  "error": "INVALID_REFERENCE",
	  "message": "Domain ID 999 does not exist",
	  "field": "domain_id"
	}
	```
	**Notes**:
	
	- Backend assigns `record_id`, `status_id` (always 3), `created_at`, `created_by`
	- Backend validates all `_id` fields against reference tables
	- Backend validates hierarchical relationships (e.g., category belongs to selected domain)
	- Returns created record ID for potential redirection or confirmation

	### B.2 NER Extraction Endpoint
	
	**Purpose**: Extract patient and doctor names from complaint text using NLP/NER
	
	```
	POST /api/ner/extract
	```
	
	**Request Headers**:
	
	```
	Content-Type: application/json
	Authorization: Bearer <token>
	```
	
	**Request Body**:
	
	```
	{
	  "text": "تأخر كبير في تشخيص الحالة الطارئة للمريض أحمد محمد علي، وقد تم استشارة الدكتور خالد حسن"
	}
	```
	
	**Response Structure** (Success):
	
	```
	{
	  "success": true,
	  "patient_name": "أحمد محمد علي",
	  "doctor_name": "د. خالد حسن",
	  "confidence": {
	    "patient_name": 0.92,
	    "doctor_name": 0.88
	  },
	  "other_entities": [
	    {
	      "type": "LOCATION",
	      "text": "قسم الطوارئ",
	      "confidence": 0.85
	    }
	  ]
	}
	```
	
	**Response Structure** (No Entities Found):
	
	```
	{
	  "success": true,
	  "patient_name": "",
	  "doctor_name": "",
	  "confidence": {
	    "patient_name": 0.0,
	    "doctor_name": 0.0
	  },
	  "other_entities": []
	}
	```
	**Response Structure** (Error):
	
	```
	{
	  "success": false,
	  "error": "NER_ERROR",
	  "message": "NER service is temporarily unavailable"
	}
	```
	**Notes**:
	
	- NER results are **not stored** in the database; only used to assist user
	- User can edit extracted names before submission
	- Low confidence results should be reviewed carefully
	- Empty text should return empty entities (not error)
	- Consider timeout for long texts

	## Section C: Assumptions / Open Questions / Risks
	
	### C.1 Assumptions
	
	1. **No Draft Support**:
	    
	    - Records must be fully completed before submission
	    - No partial save or "Save as Draft" functionality
	    - Users must complete the form in one session
	2. **Initial Status**:
	    
	    - All new records start with `status_id = 3` ("In Progress")
	    - Status cannot be set during creation
	    - Status changes happen later via edit/workflow
	3. **NER Results Are Temporary**:
	    
	    - NER extraction results are not stored in the database
	    - They are only used to pre-fill form fields
	    - User can edit or ignore NER suggestions
	    - No tracking of NER confidence or accuracy
	4. **Target Department Handling**:
	    
	    - Code shows `target_department_ids` (array) in state but `target_department_id` (singular) in payload
	    - **Assumption**: Only one target department is supported at creation time
	    - Or: Backend accepts array but code has inconsistency
	5. **ID-Based References**:
	    
	    - All dropdowns use numeric IDs (not string labels)
	    - Frontend must fetch reference data separately
	    - Backend validates all IDs against reference tables
	6. **Hierarchical Classification**:
	    
	    - Domain → Category → Subcategory → Classification
	    - Domain and Category are required
	    - Subcategory and Classification are optional
	    - Backend must validate that Category belongs to selected Domain, etc.
	7. **User Authentication**:
	    
	    - `created_by` is derived from authenticated user context
	    - Frontend does not send `created_by` in payload
	    - Backend enforces authentication on POST endpoint
	8. **Form Validation**:
	    
	    - Client-side validation checks required fields before submission
	    - Backend also validates to prevent invalid submissions
	    - Required fields: `complaint_text`, `feedback_received_date`, `domain_id`, `category_id`, `severity_id`
	9. **Worker Type**:
	    
	    - Free-text field (not ID-based)
	    - May be typed manually or selected from dropdown (not clear from code)
	    - Consider standardizing to avoid inconsistencies
	10. **Improvement Type**:
	    
	    - Binary field: 0 = No, 1 = Yes
	    - Could be boolean but represented as integer
	    - Default is 0 (No)
	
	### C.2 Open Questions
	
	1. **Multiple Target Departments**:
	    
	    - State uses `target_department_ids` (array) but payload uses `target_department_id` (singular)
	    - Does the backend accept an array? Or only a single ID?
	    - Should the UI support multiple target departments at creation time?
	2. **Worker Type Enumeration**:
	    
	    - Is `worker_type` free-text or should it be ID-based reference data?
	    - What are the valid values (Doctor, Nurse, Clerk, Technician, etc.)?
	    - Should there be a dropdown or autocomplete?
	3. **In/Out Field**:
	    
	    - What are the exact valid values? `"IN"`, `"OUT"`, or numeric IDs?
	    - Is this required or optional?
	    - Should there be a reference table for this?
	4. **Classification Hierarchy Enforcement**:
	    
	    - If user selects Category but no Subcategory, is Classification still allowed?
	    - Or must they follow Domain → Category → Subcategory → Classification strictly?
	    - Can user skip Subcategory and go directly to Classification?
	5. **NER Confidence Thresholds**:
	    
	    - Should low-confidence NER results be shown to the user?
	    - Should there be a warning if confidence is below a threshold?
	    - Or just show all results and let user decide?
	6. **Record ID Format**:
	    
	    - Is `record_id` a human-readable string (e.g., "REC-2024-0156") or numeric?
	    - Is it auto-generated by the backend?
	    - What is the format/pattern?
	7. **Feedback Received Date Validation**:
	    
	    - Can date be in the future? Or only past/present?
	    - Should there be a reasonable range (e.g., within last 2 years)?
	    - What happens if date is very old?
	8. **Duplicate Detection**:
	    
	    - Should the backend check for duplicate records (same complaint text, same date, etc.)?
	    - Or allow duplicates without warning?
	    - Consider user error or spam submissions
	9. **Patient/Doctor Name Privacy**:
	    
	    - Should patient names be stored as-is or anonymized/hashed?
	    - Are there privacy regulations to consider?
	    - Should doctor names be linked to actual employee records?
	10. **Reference Data Caching**:
	    
	    - Should reference data be cached on the frontend?
	    - How often does reference data change?
	    - Should there be a cache invalidation mechanism?
	11. **Form Reset After Submission**:
	    
	    - Code resets form after 2 seconds - is this desired UX?
	    - Should user be redirected to view/edit the created record?
	    - Or stay on the same page to create another record?
	12. **Validation Error Handling**:
	    
	    - If backend returns validation errors, how should UI display them?
	    - Field-level errors or global message?
	    - Should invalid fields be highlighted?
	
	### C.3 Risks
	
	1. **Incomplete Validation**:
	    
	    - Client-side validation only checks 5 required fields
	    - Other fields may have business rules (e.g., if severity is High, harm cannot be No Harm)
	    - Backend must enforce all validation rules
	2. **Reference Data Staleness**:
	    
	    - If reference data changes while user is filling form, selections may become invalid
	    - E.g., category is deleted while user is selecting subcategory
	    - Need stale data handling or validation on submit
	3. **NER Service Downtime**:
	    
	    - If NER service is unavailable, form should still work (NER is optional)
	    - UI should gracefully handle NER errors
	    - Consider fallback to manual entry
	4. **Large Reference Data**:
	    
	    - If there are hundreds of categories/classifications, dropdown performance may suffer
	    - Consider pagination, search, or lazy loading
	    - Or fetch only relevant data based on selections
	5. **Hierarchical Data Consistency**:
	    
	    - If user selects Category 12 (Domain 1) but then changes Domain to 2, Category 12 is now invalid
	    - UI should clear dependent selections when parent changes
	    - Backend should validate hierarchy on submit
	6. **Patient/Doctor Name Ambiguity**:
	    
	    - Multiple patients/doctors may have similar names
	    - NER may extract wrong person if names are common
	    - Consider linking to actual patient/doctor IDs instead of free text
	7. **Missing Required Fields**:
	    
	    - Code checks required fields before submit, but what if user bypasses UI (e.g., API call)?
	    - Backend must enforce all required field constraints
	    - Return clear error messages for missing fields
	8. **Record ID Collision**:
	    
	    - If record_id is auto-generated, ensure uniqueness
	    - Handle race conditions if multiple records created simultaneously
	    - Use database constraints or unique index
	9. **Long Text Truncation**:
	    
	    - `complaint_text` may be very long (multi-paragraph)
	    - Ensure backend can handle large text fields (e.g., TEXT vs VARCHAR)
	    - Consider character limits and validation
	10. **Date/Time Zones**:
	    
	    - `feedback_received_date` is date-only (no time component)
	    - Ensure consistent handling across timezones
	    - Server should store in UTC or local hospital timezone
	11. **Worker Type Typos**:
	    
	    - If worker_type is free-text, typos/variations may occur (Doctor, Dr, doctor, etc.)
	    - Consider normalization or dropdown with predefined values
	    - May affect reporting and analytics
	12. **Form Abandonment**:
	    
	    - User may start form but not complete it
	    - No draft save means data is lost
	    - Consider warning before navigating away
	13. **Target Department Missing**:
	    
	    - Code shows `target_department_id` in payload but initializes as array
	    - If singular, ensure UI only allows single selection
	    - If array, ensure backend accepts array and UI sends correctly
	14. **Improvement Type Ambiguity**:
	    
	    - 0/1 representation may be unclear to users
	    - Consider boolean or Yes/No enum for clarity
	    - Ensure consistent interpretation in backend
	15. **Arabic Text Encoding**:
	    
	    - Ensure proper UTF-8 encoding for Arabic text in complaint_text, patient_name, etc.
	    - Test with diacritics, mixed English/Arabic, and special characters
	    - Validate NER works correctly with Arabic text
