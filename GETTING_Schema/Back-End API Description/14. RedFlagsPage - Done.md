## Section A: Data Needs

### A.1 Red Flag Record (Core Data)

| Field             | Type           | Description                                                                | Derivation |
| ----------------- | -------------- | -------------------------------------------------------------------------- | ---------- |
| `id`              | Integer/String | Unique red flag identifier                                                 | Raw        |
| `recordID`        | String         | Human-readable record identifier (e.g., "RF-2024-001")                     | Raw        |
| `date`            | ISO Date       | Date the red flag incident occurred                                        | Raw        |
| `patientName`     | String         | Patient name (Arabic, may be anonymized)                                   | Raw        |
| `patientID`       | String         | Patient identifier (optional, for linking)                                 | Raw        |
| `redFlagType`     | String         | Red flag type/classification (English)                                     | Raw        |
| `redFlagTypeAr`   | String         | Red flag type/classification (Arabic)                                      | Raw        |
| `redFlagCategory` | String         | Category (e.g., "Medication Safety", "Patient Safety", "Clinical Process") | Raw        |
| `status`          | Enum           | `"OPEN"`, `"UNDER_REVIEW"`, `"FINISHED"`                                   | Raw        |
| `severity`        | Enum           | `"HIGH"`, `"CRITICAL"` (red flags are high-risk by definition)             | Raw        |
| `department`      | String         | Department where red flag occurred                                         | Raw        |
| `qism`            | String         | Section/unit (Arabic)                                                      | Raw        |
| `isNeverEvent`    | Boolean        | Whether this red flag is also a Never Event                                | Raw        |

**Note**: A red flag is a critical incident that requires immediate attention. May overlap with Never Events.

---

### A.2 Linked Incident Data (For Details Modal)

| Field | Type | Description |
|-------|------|-------------|
| `incidentID` | String | Reference to parent incident record |
| `complaintText` | Text | Original complaint/incident description |
| `immediateAction` | Text | Immediate actions taken |
| `corrective_actions` | Text | Corrective actions implemented |
| `rootCause` | Text | Root cause analysis (if completed) |
| `responsiblePerson` | String | Person responsible for follow-up |
| `targetDepartment` | String | Department responsible for resolution |
| `harmLevel` | String | Level of harm caused (e.g., "Minor", "Moderate", "Major") |
| `stage` | String | Care stage (Admission, Care, Discharge) |

**Note**: Red flags are always linked to an underlying incident record.

---

### A.3 KPI Summary (Aggregated Data)

| Field | Type | Description | Derivation |
|-------|------|-------------|------------|
| `totalRedFlags` | Integer | Total count of all red flags | **Aggregated** |
| `unfinishedCount` | Integer | Count of red flags not yet finished | **Aggregated** (where `status !== "FINISHED"`) |
| `finishedCount` | Integer | Count of finished red flags | **Aggregated** (where `status === "FINISHED"`) |
| `currentMonthCount` | Integer | Red flags in current month (optional) | **Aggregated** |
| `previousMonthCount` | Integer | Red flags in previous month (optional) | **Aggregated** |
| `neverEventOverlap` | Integer | Red flags that are also Never Events | **Aggregated** (where `isNeverEvent === true`) |

**Note**: Never Event overlap provides important cross-reference metric.

### A.4 Trend Chart Data (Time Series)

| Field | Type | Description | Derivation |

| `count` | Integer | Red flags in this period | **Aggregated** |
| `categoryBreakdown` | Object | Breakdown by red flag category (optional) | **Aggregated** |
| `severityBreakdown` | Object | Breakdown by severity (optional) | **Aggregated** |

### B.5 Export Red Flag as PDF

**Purpose**: Generate a PDF report for a specific red flag (for governance documentation)

```
POST /api/red-flags/{red_flag_id}/export-pdf
```

**Path Parameters**:
| Parameter | Type | Description |
|-----------|------|-------------|
| `red_flag_id` | Integer/String | Red flag unique identifier |

**Request Body** (optional):
```json
{
  "include_timeline": true,
  "include_actions": true,
  "include_incident_details": true,
  "language": "ar"
}
```

**Response** (PDF file):
```
Content-Type: application/pdf
Content-Disposition: attachment; filename="red_flag_RF-2024-001_2024-12-17.pdf"

[Binary PDF data]
```

**Alternative Response** (Async generation):
```json
{
  "success": true,
  "message": "PDF generation initiated",
  "job_id": "pdf-job-12345",
  "estimated_time": "30 seconds",
  "download_url": "/api/red-flags/download-pdf/pdf-job-12345"
}
```

**Notes**:
- PDF should include red flag header, incident details, timeline, and actions
- May be generated synchronously (small PDFs) or asynchronously (large/complex)
- Export action should be logged for audit trail (who, when, which red flag)
- PDF should be watermarked or marked as "CONFIDENTIAL"
- Language parameter allows Arabic or English PDF generation

## Section C: Assumptions / Open Questions / Risks

### C.1 Assumptions

1. **Red Flag Definition**:
   - A red flag is a high-risk incident that requires immediate attention and follow-up
   - Red flags are identified by specific criteria (severity, category, harm potential)
   - Red flags are a subset of incidents (not all incidents are red flags)
   - Red flags can overlap with Never Events but are not synonymous

2. **Red Flag vs Never Event**:
   - Red flags are broader: any high-risk incident requiring governance attention
   - Never Events are stricter: zero-tolerance events that should never occur
   - Some Never Events are also Red Flags, but not all Red Flags are Never Events
   - `isNeverEvent` flag indicates overlap

3. **Red Flag - Incident Relationship**:
   - Each red flag is linked to exactly one incident record
   - An incident can be flagged as a red flag during creation or review
   - Red flag designation is immutable once assigned (cannot be un-flagged)

4. **Status Lifecycle**:
   - Red flags start as `"OPEN"`
   - Progress to `"UNDER_REVIEW"` during investigation
   - End as `"FINISHED"` once fully resolved and documented
   - Status transitions are controlled (not freely editable)
   - Once `"FINISHED"`, red flags cannot be reopened without special authorization

5. **Severity Levels**:
   - Red flags are either `"HIGH"` or `"CRITICAL"` severity (no "Low" or "Medium")
   - `"CRITICAL"` red flags require immediate executive notification
   - Severity is assigned based on harm potential, not actual outcome

6. **Patient Privacy**:
   - Patient names may be anonymized or masked in some views
   - Patient ID is available but may be redacted in exports
   - Full patient details require additional authorization

7. **Search Behavior**:
   - Search is client-side in current implementation (filters already-fetched data)
   - Production should support server-side search for performance
   - Search matches across recordID, patientName, and redFlagTypeAr

8. **Trend Chart Granularity**:
   - Default granularity is monthly
   - Chart shows last 12 months by default
   - Includes months with zero red flags for continuity

9. **PDF Export Authorization**:
   - Only authorized users (quality assurance, executives, auditors) can export PDFs
   - Each export is logged for compliance (who, when, which red flag)
   - PDFs are watermarked or marked as confidential

10. **Page Access Control**:
    - Red flags page is read-only for most users
    - Status changes handled via separate workflow (not shown in this page)
    - Access restricted to quality assurance, department heads, executives

### C.2 Open Questions

1. **Red Flag Identification Criteria**:
   - What specific criteria trigger a red flag designation?
   - Is it automatic (based on severity/category) or manual (reviewer decision)?
   - Can a red flag designation be challenged or appealed?

2. **Red Flag Types**:
   - What are all the valid red flag types/categories?
   - Are they hospital-specific or based on international standards?
   - How are red flag types different from Never Event types?

3. **Never Event Overlap Logic**:
   - Are all Never Events automatically red flags?
   - Or can a Never Event exist without being a red flag?
   - How is the overlap tracked and reported?

4. **Status Transitions**:
   - Who can change red flag status?
   - Are there required steps before marking as FINISHED (e.g., corrective actions complete)?
   - Is there an approval workflow for status changes?

5. **Historical Reclassification**:
   - Can an old incident be retroactively flagged as a red flag?
   - Can a red flag be downgraded to a regular incident?
   - What is the audit trail for such changes?

6. **Severity Assignment**:
   - How is severity (`HIGH` vs `CRITICAL`) determined?
   - Can severity be changed after initial assignment?
   - Who has authority to assign severity?

7. **Trend Analysis Goals**:
   - What is the target trend? (Reduction in red flags over time?)
   - Are there thresholds or targets that trigger alerts?
   - Should trend chart show comparison to benchmarks?

8. **Patient Name Anonymization**:
   - Should patient names be anonymized in list view?
   - Or only in exports/reports?
   - What is the hospital's privacy policy for red flag records?

9. **Department Attribution**:
   - If a red flag involves multiple departments, which is primary?
   - Can a red flag be reassigned to a different department?
   - How are cross-departmental red flags tracked?

10. **PDF Export Scope**:
    - Should PDF include full incident details or summary only?
    - Should it include related actions and timeline?
    - What language should PDF be in (Arabic, English, both)?

11. **Batch Export Authorization**:
    - Who can perform batch exports (all red flags in a period)?
    - Should batch exports require approval or special permissions?
    - How are large batch exports delivered (email, download link)?

12. **Follow-Up Action Linkage**:
    - Must every red flag have at least one follow-up action?
    - Or can red flags be closed without actions (e.g., no harm, resolved immediately)?
    - How is action completion tracked?

### C.3 Risks

1. **Privacy and Confidentiality**:
   - Red flags often involve serious patient harm or near-misses
   - Patient names and details must be carefully protected
   - Need clear policy on who can access red flag data

2. **Regulatory Compliance**:
   - Red flags may have mandatory reporting requirements (internal or external)
   - Failure to properly track or report may have legal consequences
   - System must support compliance workflows

3. **Data Quality**:
   - Inconsistent red flag type naming may fragment trend data
   - Manual categorization may lead to errors
   - Need standardized taxonomy and validation

4. **Status Transition Integrity**:
   - If status can be freely changed, audit trail may be lost
   - Need controlled workflow with authorization checks
   - Risk of premature closure or reopening of critical cases

5. **Performance with Large Datasets**:
   - If hospital has hundreds of red flags, list queries may be slow
   - Need pagination and efficient filtering
   - Trend aggregation may be expensive without caching

6. **Search Accuracy**:
   - Client-side search may miss matches due to Arabic text encoding
   - Server-side search needed for production
   - Need proper text normalization and indexing

7. **KPI Staleness**:
   - If KPIs are not real-time, users may see outdated counts
   - Need clear "Last Updated" timestamp
   - Consider caching strategy for statistics

8. **Trend Interpretation**:
   - Increasing red flags may indicate better detection, not worsening safety
   - Need clear communication of what trends mean
   - Consider adding context or annotations to charts

9. **Incomplete Red Flag Records**:
   - If incident details are missing, modal may show incomplete information
   - Need graceful handling of null/empty fields
   - Consider validation rules for red flag completeness

10. **Cross-Referencing Issues**:
    - If incident is deleted or archived, red flag link may break
    - Need referential integrity checks
    - Consider soft-delete or archival instead of hard delete

11. **PDF Export Sensitivity**:
    - PDF exports of red flags are highly sensitive
    - Need encryption and access logging
    - Consider watermarking or restricted distribution

12. **Red Flag Duplication**:
    - Same incident flagged multiple times as red flag
    - Need validation to prevent duplicates
    - Or clarify if one incident can have multiple red flag types

13. **Localization Consistency**:
    - Red flag types should have both English and Arabic names
    - Inconsistent translations may confuse users
    - Need standardized bilingual taxonomy

14. **Timeline Accuracy**:
    - Timeline events must be accurately timestamped
    - User attribution required for accountability
    - Need comprehensive audit logging

15. **Related Actions Tracking**:
    - Red flags may generate multiple follow-up actions
    - Actions may span months
    - Need clear linkage and tracking to closure

16. **Never Event Overlap Confusion**:
    - Users may not understand difference between red flags and Never Events
    - Need clear documentation and UI indicators
    - Consider educational tooltips or help text

17. **Severity Escalation**:
    - If severity changes from HIGH to CRITICAL mid-investigation, how is this tracked?
    - Should there be automatic notifications for severity changes?
    - Need audit trail for severity adjustments

18. **Export Audit Trail**:
    - All PDF exports should be logged with user, timestamp, and red flag ID
    - Exports may be reviewed during audits or investigations
    - Need comprehensive export logging system

This comprehensive API contract design provides a complete foundation for implementing the RedFlagsPage with appropriate governance, privacy, and security considerations, while maintaining consistency with the NeverEventsPage structure.
