## Section A: Data Needs

### A1. Record/Incident (Core Entity)

| Field Name | Type | Description | Source Type |
|------------|------|-------------|-------------|
| `id` | Integer | Primary record identifier | Raw |
| `complaint_number` | String | Human-readable complaint reference (e.g., "C-2024-001234") | Raw |
| `complaint_text` | Text | Original complaint narrative (English) | Raw |
| `complaint_text_ar` | Text | Arabic complaint narrative | Raw |
| `complaint_summary` | Text | Short summary/excerpt for table display (first 100 chars) | Derived |
| `received_date` | Date | Date complaint received (YYYY-MM-DD) | Raw |
| `received_datetime` | DateTime | Full timestamp of receipt | Raw |
| `incident_date` | Date | Date incident occurred (may differ from received_date) | Raw |
| `created_at` | DateTime | Record creation timestamp | Raw |
| `updated_at` | DateTime | Last modification timestamp | Raw |
| `created_by_user_id` | Integer | User who created record | Raw |
| `updated_by_user_id` | Integer | User who last updated record | Raw |

### A2. Patient Information (Minimal Display)

| Field Name | Type | Description | Source Type |
|------------|------|-------------|-------------|
| `patient_id` | Integer | Internal patient identifier | Raw |
| `patient_mrn` | String | Medical Record Number (partially masked: "MRN-***789") | Derived |
| `patient_name` | String | Patient full name (masked for privacy: "Ahmed H.") | Derived |
| `patient_age` | Integer | Age at time of incident | Raw |
| `patient_gender` | String | Gender ("M", "F") | Raw |
| `patient_gender_ar` | String | Arabic gender label ("ذكر", "أنثى") | Raw |

**Privacy Note**: Patient identifiers are masked by default in table view; full details available only in EditRecord or with explicit permission.

### A6. Status and Flags

| Field Name | Type | Description | Source Type |
|------------|------|-------------|-------------|
| `status` | String | Current status (e.g., "open", "in_progress", "closed") | Raw |
| `status_ar` | String | Arabic status label | Raw |
| `status_display` | String | Display-friendly status with icon (e.g., "🟢 Open") | Derived |
| `is_closed` | Boolean | Whether complaint is finalized | Derived |
| `closure_date` | Date | Date complaint closed (null if open) | Raw |
| `is_red_flag` | Boolean | Whether flagged as critical/high-risk | Derived |
| `is_never_event` | Boolean | Whether classified as Never Event | Derived |
| `is_improvement_opportunity` | Boolean | Whether marked as improvement opportunity (not critical) | Derived |
| `priority` | String | Priority level ("urgent", "high", "normal", "low") | Raw |
| `priority_ar` | String | Arabic priority label | Raw |

**Derivation Logic**:
- `is_red_flag`: Derived from severity_id >= threshold OR specific domain/category combinations
- `is_never_event`: Derived from classification_id matching Never Events policy list
- `is_improvement_opportunity`: Derived from harm_level="None" AND severity_id <= 2

### B1. Fetch Paginated Records (Primary Endpoint)

**Endpoint**: `GET /api/complaints`

**Purpose**: Retrieve paginated list of complaints/incidents with search and filtering.

**Request Parameters**:

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `search` | String | Optional | Free-text search across complaint_number, patient_name, complaint_text |
| `issuing_dept_id` | Integer | Optional | Filter by issuing department |
| `target_dept_id` | Integer | Optional | Filter by target department |
| `dayra_id` | Integer | Optional | Filter by primary department (hierarchical) |
| `source` | String | Optional | Filter by source (e.g., "patient", "staff") |
| `status` | String | Optional | Filter by status (e.g., "open", "closed") |
| `severity_id` | Integer | Optional | Filter by severity level |
| `domain_id` | Integer | Optional | Filter by HCAT domain |
| `category_id` | Integer | Optional | Filter by category |
| `is_red_flag` | Boolean | Optional | Filter by red flag status |
| `is_never_event` | Boolean | Optional | Filter by Never Event status |
| `year` | Integer | Optional | Filter by year |
| `month` | Integer | Optional | Filter by month |
| `start_date` | Date | Optional | Filter by received_date >= start_date |
| `end_date` | Date | Optional | Filter by received_date <= end_date |
| `sort_by` | String | Optional | Sort field (default: "received_date") |
| `sort_order` | String | Optional | "asc" or "desc" (default: "desc") |
| `page` | Integer | Optional | Page number (default: 1) |
| `page_size` | Integer | Optional | Results per page (default: 50, max: 500) |
| `view` | String | Optional | View preset (e.g., "complete", "simplified") - affects returned fields |

## Section C: Assumptions, Open Questions, and Risks

### C1. Assumptions

#### Data Loading Strategy
1. **Server-Side Pagination**: Assumed table uses server-side pagination with default page size of 50 records.
2. **Server-Side Filtering**: All filtering and search operations performed on backend; frontend sends filter parameters and receives filtered results.
3. **Default Sorting**: Records sorted by `received_date DESC` by default (newest first).
4. **Lazy Loading**: Records loaded on demand (per page); no full dataset preload.

#### Search Behavior
5. **Free-Text Search Scope**: Search parameter searches across:
   - `complaint_number` (exact or partial match)
   - `patient_name` (partial match, case-insensitive)
   - `complaint_text` (full-text search, case-insensitive)
6. **Search Performance**: Search uses database indexing on `complaint_number`, `patient_name`, and full-text index on `complaint_text`.
7. **Wildcard Support**: Search automatically applies wildcard matching (e.g., "Ahmed" matches "Ahmed Hassan").

#### Patient Privacy
8. **Masked Patient Data**: By default, patient identifiers are masked in table view:
   - `patient_mrn`: Shows "MRN-***789" (last 3 digits only)
   - `patient_name`: Shows "Ahmed H." (first name + last initial)
9. **Full Patient Data Access**: Full patient details available only:
   - In single record view (`GET /api/complaints/{id}`)
   - When navigating to EditRecord
   - For users with "view_patient_identifiers" permission
10. **Export Masking**: Patient identifiers masked in exports unless `include_patient_identifiers=true` (restricted to authorized roles).

#### Filtering Logic
11. **Multi-Filter Combination**: Multiple filters are combined with AND logic (e.g., `issuing_dept_id=12 AND source=patient AND status=open`).
12. **Hierarchical Department Filtering**: Filtering by `dayra_id` (primary department) includes all child departments (qism level).
13. **Date Range Filtering**: `start_date` and `end_date` filter on `received_date` (not `incident_date`).
14. **Boolean Filters**: Filters like `is_red_flag=true` show only red flags; omitting parameter shows all records.

#### Table Views
15. **View Presets**: "Views" are predefined column configurations (complete, simplified, red flags only).
16. **View Storage**: Views can be either:
   - **Frontend-only**: Stored in React state or localStorage (simpler, no backend needed)
   - **Server-defined**: Fetched from `/api/complaints/views` endpoint (assumed for this design)
17. **Custom Views**: Users cannot create custom views in Iteration 1 (future feature).

#### Export Behavior
18. **Export Scope**: Export uses same filters as current table view (synchronized).
19. **Export Formats**: Supports CSV and JSON formats.
20. **Export File Retention**: Export files expire after 24 hours and are automatically purged.
21. **Export Audit**: All export actions logged with user ID, timestamp, filters, record count.

#### Permissions and Access Control
22. **Role-Based Record Visibility**: Users may see different records based on role:
   - **Super Admin**: All records
   - **Department Manager**: Only records where `issuing_dept_id` or `target_dept_id` matches their department
   - **Quality Staff**: All records (read-only)
23. **Edit Permissions**: `can_edit` flag determined by:
   - User role (admin, department manager)
   - Record status (cannot edit closed records)
   - Department ownership (can edit only own department's records)
24. **Delete Permissions**: `can_delete` flag determined by:
   - User role (only super admin)
   - Record age (cannot delete records >30 days old)
   - Record status (cannot delete closed records)

### C2. Open Questions

#### Pagination and Performance
1. **Maximum Page Size**: Is 500 records per page a hard limit, or configurable per user preference?
2. **Total Record Count**: Should API return total count on every request, or only when explicitly requested (performance optimization)?
3. **Cursor-Based Pagination**: For very large datasets (>10,000 records), should system use cursor-based pagination instead of offset-based?
4. **Lazy Loading vs Infinite Scroll**: Does UI use traditional pagination buttons, or infinite scroll (affects API design)?

#### Search Functionality
5. **Advanced Search**: Should system support advanced search operators (e.g., exact phrase with quotes, exclusion with minus sign)?
6. **Search Highlighting**: Should API return matched text snippets with highlights (like Google search results)?
7. **Search History**: Should system store recent searches per user for quick re-application?
8. **Autocomplete**: Should search field provide autocomplete suggestions (patient names, complaint numbers)?

#### Filtering and Views
9. **Filter Persistence**: Should applied filters persist across sessions (stored in user preferences), or reset on page reload?
10. **Filter Presets**: Can users save custom filter combinations as named presets (e.g., "My ER Open Cases")?
11. **View Customization**: Can users customize which columns appear in each view, or are views fixed?
12. **Default View**: Is default view global (all users see "complete" view), or per-user preference?

#### Patient Privacy and Masking
13. **Masking Rules**: Are masking rules global, or configurable per role/department?
14. **Audit Trail for Full Access**: If user views full patient data (unmasks), is this logged separately from export audit?
15. **Dynamic Masking**: Can masking be toggled on/off in UI (for authorized users), or always enforced?

#### Department Filtering
16. **Issuing vs Target**: When user filters by "department", does it search:
   - Only `issuing_dept_id`?
   - Only `target_dept_id`?
   - Both (OR logic)?
   - Separate filters for each (current assumption)?
17. **Hierarchical Filtering Depth**: When filtering by parent department (Idara), does it include:
   - Only direct children (Dayra)?
   - All descendants (Dayra + Qism)?
   - Configurable depth?

#### Record Status and Flags
18. **Status Workflow**: What is complete status workflow (open → in_progress → closed), and can statuses be skipped?
19. **Red Flag Criteria**: What determines `is_red_flag`? Is it:
   - Manual flag by user?
   - Auto-calculated from severity + domain + harm level?
   - Policy-defined rules?

   - Hardcoded in backend?
   - Configurable in SettingPage policies?
   - Imported from external standard (e.g., WHO)?

#### Export Functionality
21. **Export Size Limits**: Maximum record count for single export (to prevent server overload)?

   - Split into multiple files?
   - Use background job and email download link?
   - Stream directly without caching?

24. **Export Scheduling**: Should system support scheduled recurring exports (e.g., weekly CSV of all open cases)?

25. **Direct Edit Link**: Does table row click navigate to EditRecord (`/edit/{id}`), or open modal?
26. **Bulk Actions**: Can users select multiple records for bulk operations (export selected, bulk status change)?
27. **Record Locking**: When user navigates to EditRecord, is record locked to prevent concurrent edits?

28. **Real-Time Updates**: If record is updated elsewhere (by another user), does table auto-refresh or show stale data until manual refresh?

30. **Filter Options Staleness**: If new department is added in SettingPage, when does it appear in filter dropdowns (immediate, next page load, manual refresh)?

### C3. Identified Risks

#### Performance Risks
1. **Slow Free-Text Search**: Full-text search on `complaint_text` may be slow on large datasets (>100,000 records) without proper indexing or search engine integration (Elasticsearch).
2. **Unindexed Filters**: Filtering by combinations of `issuing_dept_id`, `target_dept_id`, `source`, `status` may cause slow queries if database lacks composite indexes.
3. **Large Result Sets**: Users requesting page_size=500 with complex filters may cause high memory usage and slow response times.
4. **Counting Overhead**: Returning `total_records` on every paginated request requires full table scan (or count query), which may be expensive.

#### Privacy and Security Risks
5. **Patient Data Leakage**: If masking logic has bugs, full patient identifiers (MRN, name) may leak in table view or exports.
6. **Unauthorized Export Access**: Download URLs (`/api/complaints/download/{export_id}`) may be accessible without authentication if not properly secured.
7. **Export File Retention Failure**: If purge job fails, export files containing patient data may persist indefinitely, violating retention policies.
8. **Role-Based Access Bypass**: If role-based filtering is implemented in frontend only (not backend), users may bypass by directly calling API with different parameters.

#### Data Integrity Risks
9. **Derived Field Inconsistency**: If `is_red_flag`, `is_never_event`, or other derived fields are calculated inconsistently (frontend vs backend), table may show different values than EditRecord or ReportingPage.
10. **Stale Filter Options**: If filter options endpoint (`/api/complaints/filter-options`) is cached aggressively, new departments or statuses may not appear in dropdowns.
11. **Orphaned Records**: If referenced department or doctor is deleted in SettingPage, table may show blank department names or broken links.
12. **Status Inconsistency**: If record status is updated externally (bulk import, database script), table may show "in_progress" while EditRecord shows "closed".

#### User Experience Risks
13. **Pagination Confusion**: If user applies filters on page 5 and no results match page 5, API returns empty array; user may think filters broke the system (should redirect to page 1).
14. **Export Timeout**: Large exports (>10,000 records) may timeout on client or server side, causing user to re-trigger duplicate exports.
15. **No Progress Feedback**: For slow queries (>5 seconds), user has no indication that request is processing (recommend loading indicator).
16. **Column Overload**: "Complete" view with 15+ columns may be overwhelming and cause horizontal scrolling (recommend responsive design or column hiding).

#### Search and Filtering Risks
17. **Ambiguous Search Results**: Searching "Ahmed" may return hundreds of results; without result ranking or highlighting, user cannot identify most relevant match.
18. **Filter Conflict**: If user selects `is_red_flag=true` and `is_improvement_opportunity=true` simultaneously (mutually exclusive), API returns empty result; user may think system is broken.
19. **Date Range Validation**: If `start_date > end_date`, API should return error, but if not validated, may return unexpected results or all records.
20. **Special Characters in Search**: If search contains SQL special characters (e.g., `%`, `_`, `'`), improper escaping may cause SQL errors or injection vulnerabilities.

#### Export Risks
21. **CSV Encoding Issues**: If complaint_text contains Arabic text, CSV export may have encoding errors (UTF-8 vs Windows-1256) when opened in Excel.
22. **Excel Formula Injection**: If complaint_text starts with `=`, Excel may interpret it as formula, causing security warning or code execution.
23. **Large File Download**: 10MB+ export files may fail to download on slow connections; recommend resumable download or chunked streaming.
24. **Export Audit Log Failure**: If audit logging fails silently, export actions may go unrecorded, creating compliance gap.

#### Permission and Authorization Risks
25. **Privilege Escalation**: If `can_edit` flag is determined in frontend only, malicious user may edit read-only records by directly calling EditRecord API.
26. **Department-Based Access Bypass**: If role-based filtering is implemented incorrectly, department manager may see records from other departments by manipulating filter parameters.
27. **Edit Lock Race Condition**: If two users navigate to EditRecord for same complaint simultaneously without locking, concurrent edits may overwrite each other.

#### Navigation Risks
28. **Broken Edit Links**: If record is deleted between table load and user clicking "Edit", navigation to `/edit/{id}` returns 404 error without graceful handling.
29. **Stale Record Data**: If user leaves table open for hours and clicks "Edit", they navigate to EditRecord with outdated data (recommend refresh prompt).
30. **Deep Link Persistence**: If user applies complex filters and shares URL, filter parameters may not persist correctly (require URL parameter encoding).
