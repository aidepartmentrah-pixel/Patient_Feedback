## Section A: Data Needs

### A1. Department (Organizational Structure)

| Field Name | Type | Description | Source Type |
|------------|------|-------------|-------------|
| `id` | Integer | Primary department identifier (dayra_id) | Raw |
| `name` | String | Department name (English) | Raw |
| `name_ar` | String | Department name (Arabic) | Raw |
| `code` | String | Department code/abbreviation (e.g., "ER", "SURG") | Raw |
| `parent_id` | Integer | Parent department ID (null for root-level departments) | Raw |
| `level` | Integer | Hierarchy level (1=Idara, 2=Dayra, 3=Qism) | Derived |
| `mapping_mode` | String | "internal" or "external" | Raw |
| `is_active` | Boolean | Whether department is currently active | Raw |
| `is_external` | Boolean | Whether department is external (third-party) | Derived |
| `display_order` | Integer | Sort order for display | Raw |
| `created_at` | DateTime | When department was created | Raw |
| `updated_at` | DateTime | Last modification timestamp | Raw |
| `created_by_user_id` | Integer | User who created this department | Raw |
| `updated_by_user_id` | Integer | User who last updated this department | Raw |

**Hierarchical Structure Fields** (for tree navigation):

| Field Name | Type | Description | Source Type |
|------------|------|-------------|-------------|
| `children` | Array | Child departments (nested structure) | Derived |
| `path` | String | Hierarchical path (e.g., "/1/12/45") | Derived |
| `depth` | Integer | Depth in hierarchy (0=root) | Derived |
| `has_children` | Boolean | Whether department has sub-departments | Derived |

**Usage Reference**:
- Reused in: InsertRecord, EditRecord, TableView, ReportingPage, InvestigationPage, DashboardPage, DoctorHistoryPage
- Critical for: Organizational filtering, hierarchical statistics, department assignment

### A3. Variable Attribute (System Enumerations)

| Field Name | Type | Description | Source Type |
|------------|------|-------------|-------------|
| `attribute_type` | String | Attribute category (e.g., "severity", "domain", "category", "stage", "harm_level", "status") | Raw |
| `attribute_type_label` | String | Human-readable attribute type label | Raw |
| `attribute_type_label_ar` | String | Arabic attribute type label | Raw |
| `values` | Array | Array of attribute value objects (see below) | Raw |

**Attribute Value Object** (within Variable Attribute):

| Field Name | Type | Description | Source Type |
|------------|------|-------------|-------------|
| `id` | Integer | Attribute value ID (e.g., severity_id=1) | Raw |
| `value` | String | Attribute value label (English) | Raw |
| `value_ar` | String | Attribute value label (Arabic) | Raw |
| `code` | String | Short code/abbreviation (optional) | Raw |
| `color` | String | UI color code (e.g., "#ff0000" for high severity) | Raw |
| `display_order` | Integer | Sort order for display | Raw |
| `is_active` | Boolean | Whether value is currently active | Raw |
| `metadata` | Object | Additional key-value pairs (optional, flexible) | Raw |

**Common Attribute Types**:

| Attribute Type | Example Values | Used In |
|----------------|----------------|---------|
| `severity` | Low, Medium, High, Critical | InsertRecord, EditRecord, TableView, ReportingPage |
| `domain` | Diagnosis, Medication, Surgery, Communication (HCAT) | All pages with classification |
| `category` | Wrong Dose, Delayed Diagnosis, etc. (varies per domain) | All pages with classification |
| `classification` | Fine-grained incident types | InsertRecord, EditRecord |
| `harm_level` | None, Temporary, Permanent, Death | InsertRecord, EditRecord, TableView |
| `status` | Open, Pending, Closed, Resolved | All pages |
| `stage` | Reported, Under Investigation, Closed | FollowUpPage, TableView |
| `action_type` | Investigation, Corrective, Preventive | FollowUpPage |

**Usage Reference**:
- Reused in: **ALL pages** for dropdowns, filters, classification, status tracking
- Critical for: Consistent UI labels, bilingual support, data integrity

### A4. Policy Configuration (System Policies and Thresholds)

| Field Name | Type | Description | Source Type |
|------------|------|-------------|-------------|
| `policy_key` | String | Unique policy identifier (e.g., "hcat_threshold", "red_flag_auto_escalate") | Raw |
| `policy_name` | String | Human-readable policy name (English) | Raw |
| `policy_name_ar` | String | Arabic policy name | Raw |
| `policy_value` | String/Integer/Boolean/JSON | Policy value (flexible type) | Raw |
| `policy_type` | String | Value type ("integer", "boolean", "string", "json") | Raw |
| `category` | String | Policy category (e.g., "reporting", "investigation", "escalation") | Raw |
| `description` | Text | Policy description/purpose | Raw |
| `description_ar` | Text | Arabic description | Raw |
| `is_global` | Boolean | Whether policy applies globally or per-department | Raw |
| `scope` | String | "global" or "department" | Raw |
| `department_id` | Integer | Department ID if scope=department (null if global) | Raw |
| `updated_at` | DateTime | Last modification timestamp | Raw |
| `updated_by_user_id` | Integer | User who last updated this policy | Raw |

**Example Policy Keys**:

| Policy Key | Type | Description | Used In |
|------------|------|-------------|---------|
| `hcat_threshold_default` | Integer | Default HCAT threshold for seasonal reports | ReportingPage |
| `red_flag_auto_escalate` | Boolean | Auto-escalate red flags to governance | RedFlagsPage |
| `never_event_notification_emails` | JSON | Email list for Never Event alerts | NeverEventsPage |
| `follow_up_delay_threshold_days` | Integer | Days before action marked as delayed | FollowUpPage |
| `investigation_required_severity` | Integer | Minimum severity_id requiring investigation | InvestigationPage |
| `export_retention_hours` | Integer | Hours to retain exported files before purge | ReportingPage, RedFlagsPage |
| `patient_mrn_masking` | Boolean | Whether to mask patient MRNs in exports | ReportingPage |

**Usage Reference**:
- Reused in: ReportingPage, InvestigationPage, RedFlagsPage, NeverEventsPage, FollowUpPage
- Critical for: Dynamic system behavior, threshold evaluation, report generation logic

## Section B: API Endpoints

### B1. Fetch Departments (Hierarchical)

**Endpoint**: `GET /api/settings/departments`

**Purpose**: Retrieve all departments with hierarchical structure and optional filtering by mapping mode.

**Request Parameters**:

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `mapping_mode` | String | Optional | Filter by "internal" or "external" |
| `is_active` | Boolean | Optional | Filter by active status (default: true) |
| `include_children` | Boolean | Optional | Include nested children in response (default: true) |
| `flat` | Boolean | Optional | Return flat array instead of tree (default: false) |

**Response** (200 OK - Tree Structure):

```json
{
  "mapping_mode": "internal",
  "departments": [
    {
      "id": 1,
      "name": "Clinical Services",
      "name_ar": "الخدمات السريرية",
      "code": "CLIN",
      "parent_id": null,
      "level": 1,
      "mapping_mode": "internal",
      "is_active": true,
      "display_order": 1,
      "has_children": true,
      "children": [
        {
          "id": 12,
          "name": "Emergency Department",
          "name_ar": "قسم الطوارئ",
          "code": "ER",
          "parent_id": 1,
          "level": 2,
          "mapping_mode": "internal",
          "is_active": true,
          "display_order": 1,
          "has_children": false,
          "children": []
        }
      ]
    }
  ],
  "total_count": 45,
  "active_count": 42
}
```

**Response** (200 OK - Flat Array if `flat=true`):


### B4. Delete Department

**Endpoint**: `DELETE /api/settings/departments/{id}`

**Purpose**: Soft-delete or hard-delete a department (depending on constraints).

**Request Parameters**:

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `force` | Boolean | Optional | Force delete even if department has related records (default: false) |

**Response** (200 OK - Soft Delete):

```json
{
  "id": 46,
  "is_active": false,
  "deleted_at": "2024-04-17T14:40:00Z",
  "message": "Department deactivated successfully",
  "message_ar": "تم إلغاء تنشيط القسم بنجاح"
}
```

**Response** (409 Conflict):

```json
{
  "error": "department_has_incidents",
  "message": "Cannot delete department with 234 associated incidents. Use force=true to deactivate instead.",
  "message_ar": "لا يمكن حذف قسم يحتوي على 234 حادثة مرتبطة. استخدم force=true لإلغاء التنشيط بدلاً من ذلك.",
  "incident_count": 234
}
```

## Section C: Assumptions, Open Questions, and Risks

### C1. Assumptions

#### Authorization and Access Control
1. **Admin-Only Access**: Only users with "admin" or "system_config" roles can access SettingPage.
2. **Role-Based Permissions**: Different permission levels may exist:
   - **Super Admin**: Full access to all tabs
   - **HR Manager**: Access to Doctors tab only
   - **Department Manager**: Access to Departments tab (their department only)
   - **System Admin**: Access to Variable Attributes and Policy tabs
3. **Audit Logging Required**: All configuration changes (add/update/delete) are logged with user ID, timestamp, old/new values.

#### Data Integrity and Constraints
4. **Department Hierarchy**: Maximum 3 levels (Idara → Dayra → Qism); deeper nesting not supported.
5. **Circular References**: System prevents department parent_id from pointing to itself or descendants.
6. **Soft Delete**: Departments and doctors with associated incidents cannot be hard-deleted; they are deactivated (is_active=false).
7. **Unique Constraints**:
   - Department `code` must be unique within mapping_mode
   - Doctor `employee_id` must be unique globally
   - Doctor `license_number` must be unique globally
   - Policy `policy_key` must be unique globally

#### Mapping Mode Behavior
8. **Internal vs External**: 
   - **Internal**: Hospital's own departments
   - **External**: Third-party/partner departments (e.g., outsourced lab, external clinic)
9. **Mapping Mode Toggle**: Switching mapping_mode affects:
   - Which departments appear in filters/dropdowns across all pages
   - Reporting aggregations (may exclude external departments from KPIs)
10. **Default Mode**: System defaults to "internal" mode on page load.

#### Variable Attributes
11. **Predefined Attribute Types**: System supports fixed set of attribute types (severity, domain, category, etc.); new attribute types require code changes.
12. **Cascading Categories**: Categories are nested under domains; changing domain structure may orphan categories.
13. **Backward Compatibility**: Deactivating an attribute value (is_active=false) does not break historical records; inactive values are hidden in dropdowns but still displayed for existing incidents.

#### Policy Configuration
14. **Global vs Department Scope**:
   - **Global policies** apply to entire hospital (e.g., HCAT threshold)
   - **Department policies** override global for specific departments (e.g., investigation severity threshold for ER may be lower than global)
15. **Immediate Effect**: Policy changes take effect immediately; no server restart required.
16. **No Versioning (Assumed)**: Policy changes overwrite previous values without version history (unless snapshot feature is used).

#### Export/Import
17. **Export Format**: JSON export preserves full relational structure; CSV export flattens data (separate files for departments, doctors, etc.).
18. **File Retention**: Exported configuration files expire after 24 hours (similar to ReportingPage exports).
19. **Import Validation**: Imported data is validated before applying; invalid data triggers rollback.

### C2. Open Questions

#### Authorization and Workflow
1. **Multi-Factor Authorization**: Do critical configuration changes (e.g., deleting departments, changing policy thresholds) require approval from multiple admins or confirmation workflow?
2. **Change Notification**: Should configuration changes trigger email/SMS notifications to affected users (e.g., department managers notified when their department is deactivated)?
3. **Edit Locking**: If two admins edit same department simultaneously, how are conflicts resolved (last-write-wins, optimistic locking, pessimistic locking)?

#### Department Management
4. **Department Reassignment**: If a department is deleted/deactivated, can existing incidents be bulk-reassigned to another department, or do they remain linked to inactive department?
5. **Department Merging**: Is there a workflow to merge two departments (e.g., "Cardiology A" + "Cardiology B" → "Cardiology")?
6. **External Department Integration**: How are external departments synchronized? Manual entry only, or integration with external systems?

#### Doctor Management
7. **Doctor Reassignment**: If a doctor changes primary department, do historical incidents remain linked to old department or updated to new department?
8. **Multi-Department Doctors**: How are incidents counted for doctors working in multiple departments? Which department "owns" the incident for reporting purposes?
9. **Doctor Deactivation Impact**: If a doctor is deactivated, can new incidents still be assigned to them (e.g., historical data correction)?
10. **Doctor Authentication Integration**: Is this doctor record linked to hospital's authentication system (Active Directory, LDAP), or standalone database?

#### Variable Attributes
11. **Attribute Type Customization**: Can admins create new attribute types (e.g., "patient_nationality", "incident_location"), or is the list fixed?
12. **Domain-Category Relationship**: Are categories strictly hierarchical under domains, or can one category belong to multiple domains?
13. **Attribute Value Dependencies**: If severity "Critical" is deactivated, should system prevent incident creation with that severity, or auto-downgrade to "High"?
14. **Color Coding**: Are attribute colors used only for UI display, or do they affect system logic (e.g., red severity triggers auto-escalation)?

#### Policy Configuration
15. **Policy Validation**: Are policy values validated (e.g., threshold must be >0, email must be valid format)?
16. **Policy Defaults**: If a department-specific policy is deleted, does system fall back to global policy, or throw error?
17. **Policy History**: Is there a requirement to view historical policy values (e.g., "HCAT threshold was 50 in Q1 2024, now 60")?
18. **Policy Categories**: Can new policy categories be added dynamically, or is the list fixed?

#### Export/Import
19. **Partial Import**: Can admins import only departments without importing doctors/policies (selective import)?
20. **Import Conflict Resolution**: If imported department has same `code` as existing department, should it:
    - Overwrite existing?
    - Create duplicate with new ID?
    - Skip and log error?
21. **Export Scheduling**: Should system support scheduled automated backups (e.g., daily config snapshot)?
22. **Export Encryption**: Should exported JSON files be encrypted for security, especially if containing doctor contact info?

#### Versioning and Rollback
23. **Configuration Snapshots**: How many snapshots are retained? Is there a pruning policy (e.g., keep last 10 snapshots)?
24. **Rollback Scope**: Can admins rollback individual tabs (e.g., only restore doctors), or must rollback entire configuration?
25. **Rollback Impact**: If configuration is rolled back, do existing incidents with new classification values become invalid?

#### Performance and Scalability
26. **Large Hierarchies**: What is maximum expected department count (100s, 1000s)? Does tree rendering scale?
27. **Doctor Count**: Expected total doctors in system (100s, 1000s, 10,000s)? Does pagination suffice?
28. **Attribute Value Limits**: Maximum number of values per attribute type (e.g., 100 severity levels unlikely, but 1000 categories possible)?

### C3. Identified Risks

#### Data Integrity Risks
1. **Orphaned Records**: Deleting a department/doctor may orphan incidents, follow-up actions, or explanations if referential integrity is not enforced.
2. **Circular Hierarchy**: If parent_id validation fails, circular references in department tree will cause infinite loops in UI rendering or API queries.
3. **Duplicate Codes**: If department code uniqueness is not enforced at database level, duplicate codes may cause filter/dropdown ambiguity.
4. **Invalid Parent IDs**: If parent_id points to non-existent or inactive department, tree structure breaks.

#### Authorization Risks
5. **Privilege Escalation**: If role-based access control is not properly enforced, non-admin users may access `/api/settings/*` endpoints directly via API calls.
6. **Insufficient Audit Trail**: If audit logging fails or is not comprehensive, unauthorized configuration changes may go undetected.
7. **Session Hijacking**: If admin session tokens are compromised, attacker could modify critical system configuration (e.g., deactivate all departments).

#### Configuration Change Risks
8. **Immediate Effect Disruption**: If policy changes take effect immediately without validation, incorrect policy values (e.g., threshold=0) may break ReportingPage or InvestigationPage.
9. **No Rollback Mechanism**: Without snapshot/versioning, accidental deletion or misconfiguration may be irreversible.
10. **Cascading Failures**: Deactivating a widely-used attribute value (e.g., "Open" status) may cause widespread UI/reporting errors if not handled gracefully.

#### User Experience Risks
11. **Concurrent Edit Conflicts**: If two admins edit same department simultaneously without locking, last-write-wins may overwrite critical changes.
12. **No Change Preview**: If admins cannot preview impact of configuration changes (e.g., "3,456 incidents will be affected by deactivating this department"), they may make uninformed decisions.
13. **Accidental Deletion**: If delete action lacks confirmation dialog or "undo" capability, admins may accidentally delete critical departments/doctors.

#### Performance Risks
14. **Slow Tree Rendering**: If department hierarchy has 1000+ nodes, rendering tree structure (especially with `include_children=true`) may timeout or freeze UI.
15. **Large Export Files**: Exporting full configuration with 10,000+ doctors may produce multi-MB JSON files that exceed browser memory or API gateway limits.
16. **Unbounded Queries**: Fetching all doctors without pagination (`page_size=unlimited`) may cause database query timeout or memory exhaustion.

#### Import/Export Risks
17. **Malformed Import Data**: Importing JSON with invalid structure or missing required fields may corrupt database if validation is insufficient.
18. **Import Data Injection**: If imported JSON is not sanitized, malicious payloads (e.g., SQL injection strings in department names) may compromise security.
19. **Export Data Leakage**: Exported configuration files may contain sensitive doctor contact info (email, phone); if not properly secured, they may be leaked.
20. **File Overwrite**: If export file naming is predictable (e.g., `config_export.json`), concurrent exports may overwrite each other.

#### Mapping Mode Risks
21. **Mode Toggle Confusion**: If admins switch mapping_mode mid-session, UI may show inconsistent department lists (cached vs fresh data).
22. **Reporting Inconsistency**: If external departments are excluded from reports by default, admins may not realize their incident counts are incomplete.
23. **Lost External Data**: If mapping_mode is toggled and external departments are hidden, admins may mistakenly believe they were deleted.

#### Policy Configuration Risks
24. **Invalid Policy Values**: If policy_value validation is lax (e.g., accepts negative threshold), downstream pages (ReportingPage, InvestigationPage) may crash or produce nonsensical results.
25. **Policy Type Mismatch**: If policy_type="integer" but policy_value="abc", type casting errors may occur in backend logic.
26. **Missing Policy Defaults**: If a required policy (e.g., `hcat_threshold_default`) is deleted, pages depending on it may fail to load.

#### Audit and Compliance Risks
27. **Incomplete Audit Logs**: If audit logging is not atomic with configuration changes, system may fail to record who deleted a critical department.
28. **No Change Approval Trail**: If regulatory compliance requires approval workflow for configuration changes, lack of built-in approval system creates compliance gap.
29. **Retention Policy Violation**: If exported configuration files are not purged after 24 hours, they may violate hospital's data retention policy.

#### Backward Compatibility Risks
30. **Breaking Changes**: If attribute IDs or department IDs are reassigned after deletion/recreation, historical incidents referencing old IDs may display incorrect labels.
31. **Schema Evolution**: If new fields are added to departments/doctors in future (e.g., `department_budget`), old configuration exports may not import cleanly.
