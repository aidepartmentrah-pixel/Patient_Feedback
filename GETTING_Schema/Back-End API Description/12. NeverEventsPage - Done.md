## Section A: Data Needs

### A.1 Never Event Record (Core Data)

| Field                | Type           | Description                                                                | Derivation |
| -------------------- | -------------- | -------------------------------------------------------------------------- | ---------- |
| `id`                 | Integer/String | Unique never event identifier                                              | Raw        |
| `recordID`           | String         | Human-readable record identifier (e.g., "NE-2024-001")                     | Raw        |
| `date`               | ISO Date       | Date the never event occurred                                              | Raw        |
| `patientName`        | String         | Patient name (Arabic, may be anonymized)                                   | Raw        |
| `patientID`          | String         | Patient identifier (optional, for linking)                                 | Raw        |
| `neverEventType`     | String         | Never event type (English)                                                 | Raw        |
| `neverEventTypeAr`   | String         | Never event type (Arabic)                                                  | Raw        |
| `neverEventCategory` | String         | Category classification (e.g., "Surgical", "Medication", "Patient Safety") | Raw        |
| `status`             | Enum           | `"OPEN"`, `"UNDER_REVIEW"`, `"FINISHED"`                                   | Raw        |
| `severity`           | Enum           | Severity level if applicable                                               | Raw        |
| `department`         | String         | Department where never event occurred                                      | Raw        |
| `qism`               | String         | Section/unit (Arabic)                                                      | Raw        |

**Note**: A never event is a special category of incident with zero-tolerance significance.

---

### A.2 Linked Incident Data (For Details Modal)

| Field                | Type   | Description                             |
| -------------------- | ------ | --------------------------------------- |
| `incidentID`         | String | Reference to parent incident record     |
| `complaintText`      | Text   | Original complaint/incident description |
| `immediateAction`    | Text   | Immediate actions taken                 |
| `corrective_actions` | Text   | Corrective actions implemented          |
| `rootCause`          | Text   | Root cause analysis (if completed)      |
| `responsiblePerson`  | String | Person responsible for follow-up        |
| `targetDepartment`   | String | Department responsible for resolution   |

**Note**: Never events are always linked to an underlying incident record.

---

### A.3 KPI Summary (Aggregated Data)

| Field | Type | Description | Derivation |
|-------|------|-------------|------------|
| `totalNeverEvents` | Integer | Total count of all never events | **Aggregated** |
| `unfinishedCount` | Integer | Count of never events not yet finished | **Aggregated** (where `status !== "FINISHED"`) |
| `finishedCount` | Integer | Count of finished never events | **Aggregated** (where `status === "FINISHED"`) |
| `currentMonthCount` | Integer | Never events in current month (optional) | **Aggregated** |
| `previousMonthCount` | Integer | Never events in previous month (optional) | **Aggregated** |

---

### A.4 Trend Chart Data (Time Series)

| Field | Type | Description | Derivation |
|-------|------|-------------|------------|
| `period` | String | Time period label (e.g., "Jan 2024", "2024-Q1") | **Derived** |
| `count` | Integer | Never events in this period | **Aggregated** |
| `categoryBreakdown` | Object | Breakdown by never event category (optional) | **Aggregated** |

**Example**:
```json
{
  "period": "Nov 2024",
  "count": 3,
  "categoryBreakdown": {
    "Surgical": 1,
    "Medication": 2,

```

| Field | Type | Description |
|-------|------|-------------|

## Section C: Assumptions / Open Questions / Risks

### C.1 Assumptions

1. **Never Event Definition**:
   - A never event is a special flag or category on an incident record
   - Not all incidents are never events, but all never events are incidents
   - Never events are identified at incident creation or during review (not reclassified later)

2. **Never Event - Incident Relationship**:
   - Each never event is linked to exactly one incident record
   - An incident can only be flagged as one type of never event (not multiple)
   - Never event type is immutable once assigned

3. **Status Lifecycle**:
   - Never events start as `"OPEN"`
   - Progress to `"UNDER_REVIEW"` during investigation
   - End as `"FINISHED"` once fully resolved and documented
   - Status transitions are controlled (not freely editable)
   - Once `"FINISHED"`, never events cannot be reopened (or require special authorization)

4. **Severity**:
   - All never events are assumed to be `"HIGH"` severity by default
   - Never events are zero-tolerance by definition
   - Severity may still be captured for reporting purposes

5. **Patient Privacy**:
   - Patient names may be anonymized or masked in some views
   - Patient ID is available but may be redacted in exports
   - Full patient details require additional authorization

6. **Search Behavior**:
   - Search is client-side in current implementation (filters already-fetched data)
   - Production should support server-side search for performance
   - Search matches across recordID, patientName, and neverEventTypeAr

7. **Trend Chart Granularity**:
   - Default granularity is monthly
   - Chart shows last 12 months by default
   - Includes months with zero never events for continuity

8. **Page Access Control**:
   - Never events page is read-only for most users
   - Status changes handled via separate workflow (not shown in this page)
   - Only authorized users (quality assurance, executives) can access

9. **Embedded Mode**:
   - Page can be embedded (e.g., in Critical Issues container page)
   - Embedded mode removes duplicate layout wrapper
   - Data requirements are the same for both modes

10. **Never Event Categories**:
    - Categories are predefined (e.g., Surgical, Medication, Patient Safety, Device/Equipment)
    - Not user-defined or customizable
    - Based on international standards or hospital policy

### C.2 Open Questions

1. **Never Event Identification**:
   - How are never events identified? (Manual flag, automatic classification, clinical review?)
   - Who has authority to designate an incident as a never event?
   - Can never event designation be challenged or reversed?

2. **Never Event Types**:
   - What are all the valid never event types?
   - Are they based on a standard taxonomy (e.g., NHS Never Events list)?
   - Are types hospital-specific or internationally standardized?

3. **Status Transitions**:
   - Who can change never event status?
   - Are there required steps before marking as FINISHED (e.g., root cause analysis complete)?
   - Is there an approval workflow for status changes?

4. **Historical Reclassification**:
   - Can an old incident be retroactively flagged as a never event?
   - Can a never event be downgraded to a regular incident?
   - What is the audit trail for such changes?

5. **Reporting Obligations**:
   - Are never events reported to external authorities?
   - Is there a regulatory deadline for reporting or investigation?
   - Does the system support mandatory reporting workflows?

6. **Trend Analysis Goals**:
   - What is the target trend? (Zero never events per month/quarter?)
   - Are there thresholds or targets that trigger alerts?
   - Should trend chart show comparison to benchmarks or targets?

7. **Patient Name Anonymization**:
   - Should patient names be anonymized in list view?
   - Or only in exports/reports?
   - What is the hospital's privacy policy for never event records?

8. **Department Attribution**:
   - If a never event involves multiple departments, which is primary?
   - Can a never event be reassigned to a different department?
   - How are cross-departmental never events tracked?

9. **Time Zone Handling**:
   - Are never event dates stored with time component?
   - What time zone should be used for trend aggregation?
   - How are overnight events attributed (based on start time or end time)?

10. **Details Modal Scope**:
    - What additional details should be shown in the modal?
    - Should there be attachments, photos, or evidence documents?
    - Should there be a link to view the full incident record?

11. **Finished vs Closed**:
    - Is "FINISHED" the same as "CLOSED"?
    - Or is there a distinction (e.g., FINISHED = resolved, CLOSED = documented)?
    - What are all possible status values?

12. **Multi-Year Trends**:
    - Should trend chart support multi-year views?
    - If so, how should period labels be formatted (e.g., "2024-Q1" vs "Q1 2024")?
    - Should there be year-over-year comparison?

### C.3 Risks

1. **Privacy and Confidentiality**:
   - Never events often involve serious patient harm
   - Patient names and details must be carefully protected
   - Need clear policy on who can access never event data

2. **Regulatory Compliance**:
   - Never events may have mandatory reporting requirements
   - Failure to properly track or report may have legal consequences
   - System must support compliance workflows

3. **Data Quality**:
   - Inconsistent never event type naming may fragment trend data
   - Manual categorization may lead to errors
   - Need standardized taxonomy and validation

4. **Status Transition Integrity**:
   - If status can be freely changed, audit trail may be lost
   - Need controlled workflow with authorization checks
   - Risk of premature closure or reopening of sensitive cases

5. **Performance with Large Datasets**:
   - If hospital has hundreds of never events, list queries may be slow
   - Need pagination and efficient filtering
   - Trend aggregation may be expensive without caching

6. **Search Accuracy**:
   - Client-side search may miss matches due to Arabic text encoding
   - Server-side search needed for production
   - Need proper text normalization and indexing

7. **KPI Staleness**:
   - If KPIs are not real-time, users may see outdated counts
   - Need clear "Last Updated" timestamp
   - Consider caching strategy for statistics

8. **Trend Interpretation**:
   - Zero never events in a period is good, but chart may look "flat"
   - Need clear communication that zero is the goal
   - Consider adding target line or annotations

9. **Incomplete Never Event Records**:
   - If incident details are missing, modal may show incomplete information
   - Need graceful handling of null/empty fields
   - Consider validation rules for never event completeness

10. **Cross-Referencing Issues**:
    - If incident is deleted or archived, never event link may break
    - Need referential integrity checks
    - Consider soft-delete or archival instead of hard delete

11. **Export Sensitivity**:
    - PDF/CSV exports of never events are highly sensitive
    - Need encryption and access logging
    - Consider watermarking or restricted distribution

12. **Never Event Duplication**:
    - Same incident flagged multiple times as never event
    - Need validation to prevent duplicates
    - Or support multiple never event types per incident (if policy allows)

13. **Localization Consistency**:
    - Never event types should have both English and Arabic names
    - Inconsistent translations may confuse users
    - Need standardized bilingual taxonomy

14. **Timeline Accuracy**:
    - Timeline events must be accurately timestamped
    - User attribution required for accountability
    - Need comprehensive audit logging

15. **Related Actions Tracking**:
    - Never events may generate multiple follow-up actions
    - Actions may span months or years
    - Need clear linkage and tracking to closure
