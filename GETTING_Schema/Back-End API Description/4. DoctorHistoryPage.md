## Section C: Assumptions / Open Questions / Risks

### C.1 Assumptions

1. **Doctor Identification**:
    
    - Doctors are uniquely identified by internal [id](vscode-file://vscode-app/c:/Users/IT/AppData/Local/Programs/Microsoft%20VS%20Code/resources/app/out/vs/code/electron-browser/workbench/workbench.html) (integer/string)
    - `employeeId` is human-readable but may not be immutable
    - All API requests use internal [id](vscode-file://vscode-app/c:/Users/IT/AppData/Local/Programs/Microsoft%20VS%20Code/resources/app/out/vs/code/electron-browser/workbench/workbench.html), not `employeeId`
2. **Doctor-Incident Linkage**:
    
    - Incidents are linked to doctors through a relationship (e.g., `responsible_doctor_id` or `involved_doctors` array)
    - A single incident may involve multiple doctors, but this page shows incidents where the selected doctor is the primary responsible party
    - Or: shows ALL incidents where doctor is mentioned/involved
3. **Date Range Defaults**:
    
    - Default analytics period is **last 6 months** (based on mock data showing Jul-Dec)
    - If no date range specified, statistics and analytics use this default
    - Date range applies to incident occurrence date, not report date
4. **Active vs Inactive Doctors**:
    
    - Search endpoint returns only `active` doctors by default
    - Can filter by status to include inactive/suspended doctors
    - Inactive doctors' data is still accessible if explicitly selected
5. **Patient Privacy**:
    
    - `patientId` is shown as-is in the incidents table (e.g., "P-12345")
    - No patient names or sensitive medical information are exposed
    - Patient ID may be anonymized or masked in production
6. **Statistics Computation**:
    
    - Statistics are computed dynamically based on current incident data
    - No pre-aggregation or caching (offline server assumption)
    - Counts exclude soft-deleted or invalid incidents
7. **Category Taxonomy**:
    
    - Incident categories are standardized and consistent
    - Both English (`category`) and Arabic (`categoryAr`) names are stored
    - Category breakdown uses English names; Arabic for display if needed
8. **Monthly Trend Granularity**:
    
    - Monthly trend is aggregated by month, not day or week
    - Months with zero incidents should be included in the response (for proper chart rendering)
    - Month labels are 3-letter abbreviations (Jan, Feb, Mar, etc.)
9. **Red Flags**:
    
    - Red flag is a binary indicator (`isRedFlag: true/false`)
    - Red flag incidents are counted separately in statistics
    - Can filter incidents table to show only red flags
10. **Read-Only Page**:
    
    - No write operations (no editing doctor profile, no adding incidents)
    - Page is for analytics, review, and reporting only
    - Report generation (export) may be client-side or require separate endpoint

### C.2 Open Questions

1. **Multi-Doctor Incidents**:
    
    - If an incident involves multiple doctors, does it appear in all their histories?
    - How is "primary responsibility" determined?
    - Should there be a field indicating the doctor's role in each incident?
2. **Doctor Profile Completeness**:
    
    - Are all doctors guaranteed to have [department](vscode-file://vscode-app/c:/Users/IT/AppData/Local/Programs/Microsoft%20VS%20Code/resources/app/out/vs/code/electron-browser/workbench/workbench.html), `specialty`, `hireDate`?
    - What if some fields are missing or null?
    - Should the UI handle incomplete profiles gracefully?
3. **Date Range Flexibility**:
    
    - Should there be a date picker in the UI for custom date ranges?
    - Or is the default 6-month period sufficient for all use cases?
    - Should there be preset options (last 3 months, last year, all time)?
4. **Category Naming Consistency**:
    
    - Are category names standardized across all incidents?
    - Can category names change over time (e.g., "Medication Error" → "Medication Errors")?
    - Should the API normalize category names?
5. **Performance Metrics**:
    
    - Are there any performance benchmarks or thresholds?
    - E.g., "Doctor has more than 5 high-severity incidents in 6 months" → flagged for review?
    - Should the API include performance indicators (flags, warnings)?
6. **Pagination for Incidents**:
    
    - What is the expected max number of incidents per doctor?
    - Is pagination necessary or can all incidents be returned in one call?
    - If paginated, what is the default page size?
7. **Report Generation**:
    
    - Is report generation (export to PDF/Excel) handled by the frontend or backend?
    - If backend, what format and data should the report include?
    - Should there be a dedicated `/api/doctors/{id}/export` endpoint?
8. **Status Enum Values**:
    
    - What are all possible incident status values?
    - Mock shows `OPEN`, `UNDER_REVIEW`, `CLOSED` - are there others?
    - Is there a difference between `CLOSED` and `RESOLVED`?
9. **Time Zone Handling**:
    
    - Are dates stored in UTC or local hospital time?
    - Should the API return timezone-aware timestamps?
    - How should month boundaries be calculated for monthly trend?
10. **Access Control**:
    
    - Who is authorized to view doctor history?
    - Department heads only? Quality assurance team? Administrators?
    - Should the API enforce role-based access control?
11. **Doctor Anonymization**:
    
    - Are there scenarios where doctor names should be anonymized?
    - E.g., for external audits or research?
    - Should the API support anonymized mode?
12. **Historical Data Accuracy**:
    
    - If a doctor changes departments, how are historical incidents categorized?
    - E.g., Doctor was in ER, now in ICU - where do old ER incidents appear?
    - Is department/specialty data point-in-time or current?

### C.3 Risks

1. **Performance with High-Volume Doctors**:
    
    - Some doctors may have hundreds of incidents over time
    - Fetching all incidents without pagination could be slow
    - Consider pagination or limiting default incident list size
2. **Privacy and Confidentiality**:
    
    - Displaying patient IDs may violate privacy policies
    - Ensure patient identifiers are properly anonymized or masked
    - Consider whether incident details should be limited
3. **Stale Data**:
    
    - If statistics are computed dynamically, they may change between page loads
    - User may not realize data has updated since last view
    - Consider adding "Last Updated" timestamp
4. **Category Inconsistency**:
    
    - If category names vary (e.g., typos, variations), chart may be fragmented
    - Backend should normalize or validate category names
    - Or use category IDs instead of names for aggregation
5. **Month Label Localization**:
    
    - Month labels ("Jul", "Aug") are English - may need Arabic equivalents
    - If date range spans multiple years, month labels should include year
    - Frontend may need to handle month label formatting
6. **No Real-Time Updates**:
    
    - Page shows snapshot at load time
    - If new incidents are added while page is open, user won't see them
    - Consider refresh button or auto-refresh mechanism
7. **Doctor Deactivation**:
    
    - If a doctor is deactivated mid-analysis, what happens?
    - Should historical data remain accessible?
    - Consider showing status indicator in profile
8. **Empty States**:
    
    - What if a doctor has zero incidents?
    - Should charts show "No data" or empty state?
    - Consider how UI handles doctors with no incident history
9. **Date Range Edge Cases**:
    
    - What if `from_date > to_date`?
    - What if date range is in the future?
    - Backend should validate and return appropriate errors
10. **Large Result Sets**:
    
    - Category breakdown may have many categories
    - Monthly trend over long periods may be large
    - Consider limiting to top N categories or recent M months
11. **Report Export Performance**:
    
    - Generating PDF/Excel reports may be slow
    - Consider async report generation with download link
    - Or limit report to current visible data only
12. **Doctor Not Found**:
    
    - What if `doctor_id` doesn't exist or is invalid?
    - Should return 404 with clear error message
    - Frontend should handle gracefully and allow new search
