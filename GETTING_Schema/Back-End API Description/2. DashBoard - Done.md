## Section B: API Endpoints

### B.1 Dashboard Statistics Endpoint

**Purpose**: Retrieve aggregated dashboard statistics for a given scope

```
GET /api/dashboard/stats
```

**Query Parameters**:

| Parameter | Type | Required | Description | Example |
|-----------|------|----------|-------------|---------|
| `scope` | String | Yes | Scope level | `"hospital"`, `"administration"`, `"department"`, `"section"` |
| `administration_id` | String | Conditional | Required if scope is `"administration"`, `"department"`, or `"section"` | `"nursing"` |
| `department_id` | String | Conditional | Required if scope is `"department"` or `"section"` | `"emergency_nursing"` |
| `section_id` | String | Conditional | Required if scope is `"section"` | `"er_triage"` |
| `start_date` | ISO Date | Optional | Filter incidents from this date (default: last 30 days) | `"2025-11-17"` |
| `end_date` | ISO Date | Optional | Filter incidents until this date (default: today) | `"2025-12-17"` |

**Response Structure**:
```json
{
  "metrics": {
    "totalIncidents": 124,
    "uniquePatients": 89,
    "openClosed": { "open": 32, "closed": 92, "forciblyClosed": 12 },
```

## Section C: Assumptions / Open Questions / Risks

### C.1 Assumptions

1. **Default Time Range**: Dashboard statistics default to the last 30 days if no date range is provided. This assumption is not visible in the UI code.

2. **Trend Calculation Period**: Trends are calculated by comparing the current period to the previous period of equal length (e.g., if viewing last 30 days, compare to the 30 days before that).

3. **Trend Direction Logic**: 
   - For `incidentsPatients`, `severity`, `domain`, and `redFlags`: "up" means increase (potentially negative)
   - For `openClosed`: Direction may indicate increase in closure rate (potentially positive)
   - The UI does not clearly indicate whether "up" is good or bad—this is context-dependent

4. **Real-time vs. Pre-aggregated**: Statistics are assumed to be **computed on-demand** rather than pre-aggregated, given the offline hospital environment and need for accurate real-time data.

5. **Recent Activity Limit**: Return 5-10 most recent incidents. The exact number is not specified in the UI.

6. **Multi-hierarchy Filtering**: When viewing a lower level (e.g., Dayra), all incidents belonging to that Dayra and all child Qisms are included in the aggregation.

7. **Forcibly Closed**: The `forciblyClosed` field suggests a distinct status separate from normal closure—likely an administrative action.

### C.2 Open Questions

1. **Date Range Control**: The UI does not show any date range picker. Should the API:
   - Always use a fixed default (e.g., last 30 days)?
   - Accept optional date parameters for future filtering?
   - Use a different default per scope level?

2. **Empty Data Handling**: What should the API return when:
   - A scope has zero incidents?
   - Top 5 classifications have fewer than 5 items?
   - No trends are available (e.g., first time period)?

3. **Performance**: For hospital-wide aggregation:
   - Should there be limits on the date range to prevent slow queries?
   - Should certain heavy aggregations be pre-computed?

4. **Issuing Department Logic**: 
   - At hospital level, does `issuingDept` show top departments across ALL administrations?
   - At administration level, does it show departments within that administration only?
   - What about cross-department incidents?

5. **Red Flags Count**: Does `redFlags` count:
   - Distinct incidents marked as red flags?
   - Total number of red flag violations within incidents?
   - Only currently active red flags?

6. **Patient Privacy**: Given that `uniquePatients` is displayed, is this count:
   - Simply a count (no identifiable information)?
   - Anonymized in compliance with hospital data policies?

### C.3 Risks

1. **Performance at Hospital Scope**: Aggregating all incidents across the entire hospital could be slow without proper database indexing and query optimization.

2. **Inconsistent Hierarchies**: If the organizational structure changes over time, historical data may reference departments/sections that no longer exist or have been renamed.

3. **Stale Data in Offline Environment**: If the server is offline and data syncs periodically, the dashboard may show outdated statistics. Consider adding a "Last Updated" timestamp.

4. **No Refresh Mechanism**: The UI doesn't show any refresh button or auto-refresh logic. Users may view stale data without realizing it.

5. **Trend Calculation Edge Cases**:
   - First month of operation has no previous period for comparison
   - Scope changes mid-period (e.g., department split)
   - Zero incidents in previous period (division by zero)

6. **Large Recent Activity Feed**: Without pagination, recent activity could become unwieldy in high-incident departments.

7. **No Error States**: The UI doesn't show error handling if the API fails or returns invalid data.

8. **Classification Names**: If classification names are user-editable or change over time, the "Top 5" chart may show inconsistent labeling across different time periods.
