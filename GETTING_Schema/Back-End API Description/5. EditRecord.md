## Section B: API Endpoints

### B.1 Search Records Endpoint

**Purpose**: Search for existing records to select for editing

```
GET /api/records/search
```
**Query Parameters**:

|Parameter|Type|Required|Description|Example|
|---|---|---|---|---|
|`query`|String|❌ No|Search by record ID, patient name, or keywords|`"C-2024-0015"`|
|`record_id`|String|❌ No|Exact match by record ID|`"REC-2024-001"`|
|[department](vscode-file://vscode-app/c:/Users/IT/AppData/Local/Programs/Microsoft%20VS%20Code/resources/app/out/vs/code/electron-browser/workbench/workbench.html)|String|❌ No|Filter by issuing department|`"ER"`|

|`from_date`|ISO Date|❌ No|Filter from feedback received date|`"2024-01-01"`|
|`to_date`|ISO Date|❌ No|Filter to feedback received date|`"2024-12-31"`|
|`limit`|Integer|❌ No|Max results (default: 50)|`20`|


**Notes**:

- Returns lightweight record list for selection UI
- Should support partial matching on record_id and patient name
- Results sorted by feedback_received_date descending (most recent first)

## Section C: Assumptions / Open Questions / Risks

### C.1 Assumptions

1. **Record Identification**:
    
    - Records are uniquely identified by `record_id` (string)
    - `record_id` is immutable and cannot be changed after creation
    - URL parameter [/edit/:id](vscode-file://vscode-app/c:/Users/IT/AppData/Local/Programs/Microsoft%20VS%20Code/resources/app/out/vs/code/electron-browser/workbench/workbench.html) uses `record_id`
2. **Edit Permissions**:
    
    - Users with appropriate permissions can edit any record
    - No approval workflow or multi-level editing restrictions
    - Edit access is role-based (e.g., quality assurance team, administrators)
3. **Field Mutability**:
    
    - Most fields are editable, including core fields like `complaint_text`
    - `record_id`, `created_at` are immutable
    - No fields are locked after record creation or status changes
4. **Audit Trail**:
    
    - Backend tracks `last_updated_at` and `last_updated_by` automatically
    - Frontend does not need to send these fields in update payload
    - Full edit history may be tracked in backend audit logs (not visible in UI)
5. **NER/NLP Fields**:
    
    - Fields like `patient_full_name`, `doctor_name`, `other_entities` may have been auto-detected by NER
    - However, they are stored as regular editable text fields
    - No automatic re-extraction on edit; users manually correct if needed
6. **Validation**:
    
    - `complaint_text` is required and cannot be empty
    - `feedback_received_date` is required and must be valid date
    - All other fields are optional or have default values
    - Backend enforces validation; frontend provides client-side checks
7. **Full vs Partial Update**:
    
    - Current implementation sends all fields on update (PUT approach)
    - Backend could support partial updates (PATCH) to reduce payload size
    - Recommend PATCH for efficiency and clarity about what changed
8. **Reset Functionality**:
    
    - "Reset to Original" button restores form to state at load time
    - Does NOT fetch fresh data from server; uses cached `originalRecord`
    - User must reload page to get latest changes by other users
9. **Concurrent Editing**:
    
    - No explicit locking mechanism in UI
    - If two users edit same record, last write wins
    - Risk of data loss from concurrent edits (see C.3)
10. **Status Transitions**:
    
    - No validation on status field transitions (e.g., "Closed" can change back to "Open")
    - Status is a simple dropdown with no workflow enforcement
    - Any status value can be set at any time
11. **Department and Source Values**:
    
    - Departments and sources are likely from predefined dropdown lists
    - Values should match reference data (departments table, sources enum)
    - Backend should validate against valid values
12. **Date Handling**:
    
    - Dates stored as ISO 8601 format (YYYY-MM-DD)
    - Frontend uses date input type; no time component
    - Backend should validate date format and range

### C.2 Open Questions

1. **Record Versioning**:
    
    - Are previous versions of a record stored?
    - Can users view edit history or revert to previous versions?
    - Is there an audit log visible in the UI?
2. **Edit Permissions**:
    
    - Can any authenticated user edit any record?
    - Are there department-specific edit restrictions?
    - Can users only edit records from their own department?
3. **Field-Level Permissions**:
    
    - Are all fields editable by all authorized users?
    - Are some fields restricted to specific roles (e.g., only admins can change status)?
    - Can users edit closed/archived records?
4. **Concurrent Edit Handling**:
    
    - How should the system handle two users editing the same record simultaneously?
    - Should there be optimistic locking (compare `last_updated_at`)?
    - Should there be pessimistic locking (lock record when opened for editing)?
5. **Status Workflow**:
    
    - Are there valid status transitions (e.g., Open → In Progress → Closed)?
    - Should certain status changes trigger notifications or validations?
    - Can "Closed" records be reopened?
6. **NER Output Recalculation**:
    
    - If `complaint_text` is edited, should NER be re-run automatically?
    - Or are NER fields (patient_name, doctor_name) static after initial extraction?
    - Can users manually trigger NER re-extraction?
7. **Classification Consistency**:
    
    - If `category` or `sub_category` changes, should `classification_ar` update automatically?
    - Or are they independent editable fields?
    - How is consistency enforced between these fields?
8. **Delete or Archive**:
    
    - Can records be deleted from this page?
    - Or only edited?
    - Is there an archive/soft-delete mechanism?
9. **Search Performance**:
    
    - What is the expected total number of records in the system?
    - Is search performance adequate for full-text search?
    - Should search be indexed or use specialized search service?
10. **Validation Rules**:
    
    - Are there cross-field validation rules (e.g., if severity is High, certain fields required)?
    - Are there business rules enforced on update?
    - What are all the valid enum values for each dropdown field?
11. **Department Reference Data**:
    
    - How is the list of valid departments maintained?
    - Should the edit page fetch department list from an API?
    - Are department names localized (Arabic/English)?
12. **Patient/Doctor Linking**:
    
    - Are `patient_full_name` and `doctor_name` just free text?
    - Or should they link to actual patient/doctor records?
    - Should there be autocomplete or validation against known entities?

### C.3 Risks

1. **Concurrent Edit Conflicts**:
    
    - Two users editing the same record will cause data loss (last write wins)
    - Need optimistic locking: include `last_updated_at` in update request and validate it hasn't changed
    - Or pessimistic locking: lock record when opened for editing
2. **Missing Validation**:
    
    - Frontend validates required fields, but backend must also validate
    - Invalid data could be submitted if client-side validation is bypassed
    - Backend should enforce all validation rules and constraints
3. **Large Text Field Updates**:
    
    - `complaint_text` may be very long
    - Ensure API can handle large payloads
    - Consider size limits and character encoding (Arabic text)
4. **Stale Data**:
    
    - User opens record for editing, another user updates it, first user submits outdated changes
    - Need version control or timestamp-based conflict detection
    - Consider showing "Record has been updated" warning
5. **Audit Trail Gaps**:
    
    - If only `last_updated_at` and `last_updated_by` are tracked, no history of what changed
    - Consider storing full change history or field-level audit logs
    - May be required for compliance or investigations
6. **Performance Issues**:
    
    - Search endpoint may be slow with large dataset and full-text search
    - Consider pagination, indexing, or search optimization
    - Limit search results to prevent performance degradation
7. **Inconsistent Classification**:
    
    - If category, sub-category, and classification_ar can be edited independently, they may become inconsistent
    - E.g., classification_ar says "X > Y" but category is "Z"
    - Need validation or auto-generation of classification_ar from category hierarchy
8. **NER Data Quality**:
    
    - If NER outputs are manually edited, no way to track accuracy of NER system
    - May need flag indicating "manually corrected" vs "auto-detected"
    - Consider preserving original NER output for comparison
9. **Enumeration Value Changes**:
    
    - If valid values for status, severity, etc. change, old records may have invalid values
    - Backend should handle deprecated enum values gracefully
    - Consider migration or backward compatibility
10. **Authorization Bypass**:
    
    - If authorization is only checked on page load, API calls may be unauthorized
    - Each API endpoint must verify user permissions
    - Don't rely solely on UI access control
11. **Date Validation**:
    
    - `feedback_received_date` could be set to future date or unrealistic past date
    - Backend should validate date is within reasonable range
    - Consider business rules (e.g., can't be before hospital opening date)
12. **Arabic Text Encoding**:
    
    - Ensure proper UTF-8 encoding for Arabic text fields
    - Validate that API, database, and frontend all handle Arabic correctly
    - Test with complex Arabic text (diacritics, mixed direction)
13. **Reset vs Refresh**:
    
    - "Reset" uses cached original data, not fresh data from server
    - If record was updated by another user, reset will still show old data
    - Users may be confused by discrepancy
    - Consider adding "Refresh" button to fetch latest version
14. **No Save Draft**:
    
    - If user navigates away without saving, changes are lost
    - Consider auto-save or draft functionality
    - Or at least confirm before leaving with unsaved changes (already implemented)
15. **Error Handling**:
    
    - Network errors, server errors, validation errors need clear user feedback
    - Current implementation shows generic error messages
    - Consider more specific error messages based on error type
