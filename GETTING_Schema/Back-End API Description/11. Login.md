## Section B: API Endpoints

### B.1 Login Endpoint

**Purpose**: Authenticate user credentials and issue an authentication token

```
POST /api/auth/login
```

**Request Headers**:

``
```
Content-Type: application/json
```

**Request Body**:

```
{
  "username": "ahmed.mohamed",
  "password": "SecurePassword123!"
}
```

**Alternative Field Names** (depending on implementation):

```
{
  "employee_id": "DOC-2024-001",
  "password": "SecurePassword123!"
}
```

Or:

```
{
  "email": "ahmed.mohamed@hospital.local",
  "password": "SecurePassword123!"
}
```


**Response Structure** (Success - 200 OK):

```
{
  "success": true,
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "user": {
    "user_id": 42,
    "username": "ahmed.mohamed",
    "full_name": "Ahmed Mohamed",
    "full_name_ar": "أحمد محمد",
    "email": "ahmed.mohamed@hospital.local",
    "department": "Quality Assurance",
    "role": "admin"
  },
  "expires_at": "2025-12-18T15:30:00Z"
}
```

**Response Structure** (Authentication Failed - 401 Unauthorized):

```
{
  "success": false,
  "error": "INVALID_CREDENTIALS",
  "message": "Invalid username or password"
}
```
**Response Structure** (Account Locked - 403 Forbidden):

```
{
  "success": false,
  "error": "ACCOUNT_LOCKED",
  "message": "Account has been locked due to multiple failed login attempts"
}
```

**Response Structure** (Validation Error - 400 Bad Request):

```
{
  "success": false,
  "error": "VALIDATION_ERROR",
  "message": "Username and password are required",
  "fields": ["username", "password"]
}
```

**Notes**:

- Password transmitted over HTTPS (not stored/logged in plaintext)
- Token should be cryptographically secure (JWT or opaque token with server-side session)
- Consider rate limiting to prevent brute force attacks
- Consider account lockout after N failed attempts
- `expires_at` indicates when token expires (if applicable)

### B.2 Validate Token Endpoint (Optional)

**Purpose**: Validate if a stored token is still valid (for session restoration on page reload)

```
GET /api/auth/validate
```

**Request Headers**:

```
Authorization: Bearer <token>
```

**Response Structure** (Valid Token - 200 OK):

```
{
  "valid": true,
  "user": {
    "user_id": 42,
    "username": "ahmed.mohamed",
    "full_name": "Ahmed Mohamed",
    "department": "Quality Assurance",
    "role": "admin"
  },
  "expires_at": "2025-12-18T15:30:00Z"
}
```

**Response Structure** (Invalid/Expired Token - 401 Unauthorized):

```
{
  "valid": false,
  "error": "TOKEN_EXPIRED",
  "message": "Authentication token has expired"
}
```
**Notes**:

- Used on app initialization to verify stored token is still valid
- Allows re-fetching user info without re-login
- Can be combined with auto-refresh if token is near expiration
- Current code assumes token presence = valid; this endpoint adds proper validation

### B.3 Logout Endpoint (Optional)

**Purpose**: Invalidate authentication token (server-side session termination)

```
POST /api/auth/logout
```

**Request Headers**:

```
Authorization: Bearer <token>
```
**Request Body**: None (or empty)

**Response Structure** (Success - 200 OK):

```
{
  "success": true,
  "message": "Logged out successfully"
}
```



**Response Structure** (Already Logged Out - 200 OK):

```
{
  "success": true,
  "message": "Already logged out"
}
```
**Notes**:

- If using opaque tokens with server-side sessions, this endpoint invalidates the session
- If using stateless JWTs, logout is client-side only (delete token from localStorage)
- Consider token blacklist for JWTs if immediate revocation is required
- Frontend should clear localStorage regardless of API response

## Section C: Assumptions / Open Questions / Risks

### C.1 Assumptions

1. **Single Identifier Type**:
    
    - Users log in with a single identifier (username, employee ID, or email)
    - Not multiple options (e.g., "username OR email")
    - **Assumption**: Username or employee ID is the primary identifier
2. **Token Storage**:
    
    - Token stored in `localStorage` (key: `"authToken"`)
    - Token is sent in `Authorization: Bearer <token>` header for subsequent API calls
    - No secure cookie-based authentication in Iteration 1
3. **No Token Validation on Startup**:
    
    - Current code checks if token exists, but doesn't validate it
    - Assumes token presence = valid session
    - **Risk**: User may have expired token and won't be redirected to login until first API call fails
4. **No Role-Based Access Control (RBAC) in Iteration 1**:
    
    - All authenticated users have access to all features
    - Or: RBAC is handled by backend on individual endpoints (not exposed in login response)
    - **Assumption**: User role is informational, not used for UI-level access control
5. **Logout is Client-Side Only**:
    
    - User logs out by deleting token from localStorage
    - No server-side session invalidation
    - **Assumption**: Tokens are stateless JWTs (server doesn't track sessions)
6. **No Password Reset / Recovery**:
    
    - Iteration 1 does not include password reset functionality
    - Users with forgotten passwords must contact administrator
    - No "Forgot Password?" link in UI
7. **No Multi-Factor Authentication (MFA)**:
    
    - Authentication is single-factor (username + password only)
    - No OTP, SMS, or authenticator app support
8. **No Account Registration**:
    
    - Users cannot self-register
    - Accounts are created by administrators outside this flow
    - No "Sign Up" or "Create Account" option
9. **Offline System**:
    
    - No external authentication providers (OAuth, SAML, LDAP)
    - Authentication is internal to the hospital system
    - Suitable for air-gapped or offline deployments
10. **Session Expiration**:
    
    - Tokens have an expiration time (e.g., 8 hours, 24 hours)
    - Expired tokens require re-login
    - No automatic session extension on activity

### C.2 Open Questions

1. **Identifier Field Name**:
    
    - Is the login identifier called `username`, `employee_id`, `email`, or something else?
    - Should the API accept multiple identifier types (e.g., username OR email)?
    - What format do employee IDs follow (e.g., "DOC-2024-001")?
2. **Token Type**:
    
    - Is the token a JWT (stateless, self-contained) or opaque token (requires server-side lookup)?
    - If JWT, what claims are included (user_id, role, permissions, expiration)?
    - If opaque, how are sessions stored server-side (database, Redis, in-memory)?
3. **Token Expiration**:
    
    - How long are tokens valid (1 hour, 8 hours, 24 hours, never)?
    - Is there a sliding expiration (extends on activity)?
    - Is there a hard expiration (no extension)?
4. **Token Refresh Strategy**:
    
    - Is automatic token refresh needed in Iteration 1?
    - Should frontend detect near-expiration and request new token?
    - Or require re-login after expiration?
5. **Role and Permissions**:
    
    - Does the login response include user role/permissions?
    - Are permissions granular (e.g., `["view_reports", "edit_records"]`)?
    - Or role-based (e.g., `"admin"`, `"viewer"`, `"department_head"`)?
    - How are permissions used in the UI (hide/show features, enable/disable buttons)?
6. **User Information Caching**:
    
    - Should user info be stored in localStorage alongside token?
    - Or should it be refetched on app load using token validation endpoint?
    - How often should user info be refreshed (in case role/department changes)?
7. **Logout Behavior**:
    
    - Is logout client-side only (delete localStorage)?
    - Or should there be a server-side logout endpoint to invalidate session?
    - What happens if user logs out on one device but has token on another?
8. **Failed Login Handling**:
    
    - How many failed login attempts before account lockout?
    - Is there a cooldown period or CAPTCHA after failures?
    - Who can unlock a locked account?
9. **Password Complexity**:
    
    - Are there password complexity requirements (length, characters, etc.)?
    - Are these enforced server-side only or shown in UI as well?
    - Not applicable to login, but relevant for password changes in future
10. **Default Credentials**:
    
    - Are there default admin credentials for initial setup?
    - How are initial users created in the system?
    - Is there a bootstrap/seed process?
11. **Session Timeout on Inactivity**:
    
    - Should sessions expire after inactivity (e.g., 30 minutes idle)?
    - Or only after absolute token expiration?
    - How is inactivity detected (last API call, last user interaction)?
12. **Concurrent Sessions**:
    
    - Can a user be logged in on multiple devices/browsers simultaneously?
    - Or should new login invalidate previous session?
    - How are concurrent sessions tracked?

### C.3 Risks

1. **Token Stored in localStorage**:
    
    - localStorage is vulnerable to XSS attacks
    - If malicious script executes, token can be stolen
    - **Mitigation**: Use secure HTTP-only cookies instead (requires backend changes)
    - Or: Accept risk for Iteration 1, plan migration to cookies
2. **No Token Validation on Startup**:
    
    - Current code assumes token presence = valid
    - User with expired token will see brief flash of authenticated UI before first API call fails
    - **Mitigation**: Add token validation endpoint call on app initialization
3. **Cleartext Password Transmission**:
    
    - Password sent in JSON body (cleartext)
    - **Must** use HTTPS to encrypt in transit
    - **Risk**: If HTTPS not enforced, credentials can be intercepted
    - **Mitigation**: Enforce HTTPS at server/proxy level
4. **No Brute Force Protection**:
    
    - Without rate limiting, attackers can attempt many passwords
    - **Mitigation**: Implement rate limiting on login endpoint (e.g., 5 attempts per minute per IP)
    - Or: Account lockout after N failed attempts
5. **Expired Token Edge Cases**:
    
    - If token expires while user is actively using the app, they may lose work
    - **Mitigation**: Detect 401 responses, prompt re-login, preserve form state if possible
    - Or: Implement auto-refresh before expiration
6. **Logout Not Immediate**:
    
    - If using stateless JWTs, logout is client-side only
    - Token remains valid until expiration even after "logout"
    - **Risk**: Stolen token can be used until expiration
    - **Mitigation**: Use short-lived tokens or implement token blacklist
7. **No CSRF Protection**:
    
    - If using cookies for auth (future), need CSRF tokens
    - localStorage-based auth is not vulnerable to CSRF
    - **Note**: Not a risk for current implementation
8. **Username Enumeration**:
    
    - Different error messages for "user not found" vs "wrong password" allow enumeration
    - **Mitigation**: Use generic "Invalid username or password" message
9. **No Account Recovery**:
    
    - Users with forgotten passwords cannot self-recover
    - Dependency on administrator to reset password
    - **Risk**: Administrator overhead, delayed access
10. **Single Point of Failure**:
    
    - If authentication service is down, entire system is inaccessible
    - **Mitigation**: Ensure high availability of auth service
    - Or: Implement emergency bypass (with audit trail)
11. **Weak Password Storage**:
    
    - Passwords must be hashed with strong algorithm (bcrypt, Argon2, etc.)
    - **Risk**: If database is compromised, plaintext or weakly hashed passwords are exposed
    - **Note**: Backend implementation detail, but critical
12. **Token Leakage in Logs**:
    
    - Tokens should never be logged server-side
    - **Risk**: Logs may be compromised, exposing active sessions
    - **Mitigation**: Sanitize logs, redact Authorization headers
13. **No Session Management UI**:
    
    - Users cannot view active sessions or revoke devices
    - **Risk**: Compromised device remains authenticated indefinitely
    - **Future**: Add session management page
14. **Department/Role Changes Not Reflected**:
    
    - If user's department or role changes while logged in, token still has old info
    - **Risk**: User may have access they shouldn't, or lack access they should have
    - **Mitigation**: Force re-login on role change, or use short-lived tokens
15. **Network Failures**:
    
    - Login request may fail due to network issues
    - **Risk**: User sees generic error, unclear if credentials wrong or network issue
    - **Mitigation**: Distinguish network errors from authentication errors in UI
