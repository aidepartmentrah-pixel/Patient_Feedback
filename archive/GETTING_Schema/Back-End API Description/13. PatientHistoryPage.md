## Section A: Data Needs

### A.1 Patient Search Results (Lightweight)

| Field           | Type           | Description                           | Purpose                   |
| --------------- | -------------- | ------------------------------------- | ------------------------- |
| `patient_id`    | String/Integer | Unique patient identifier             | Primary key, selection    |
| `mrn`           | String         | Medical Record Number                 | Alternative identifier    |
| `full_name`     | String         | Patient full name (Arabic)            | Display in search results |
| `date_of_birth` | ISO Date       | Patient date of birth                 | Display, verification     |
| `gender`        | Enum           | `"Male"`, `"Female"`                  | Display                   |
| `phone`         | String         | Contact phone (partial mask optional) | Display                   |

**Note**: Minimal fields for search/selection. Full details fetched after selection.

## Section B: API Endpoints

### B.1 Search Patients

**Purpose**: Search for patients by name, MRN, or other identifiers

```
GET /api/patients/search
```

**Query Parameters**:
| Parameter | Type | Required | Description | Example |
|-----------|------|----------|-------------|---------|
| `query` | String | ❌ No | Search by name, MRN, phone | `"أحمد محمد"` |
| `mrn` | String | ❌ No | Exact match by MRN | `"MRN-123456"` |
| `phone` | String | ❌ No | Search by phone number | `"+966XXXXXXXXX"` |
| `date_of_birth` | ISO Date | ❌ No | Filter by date of birth | `"1985-05-15"` |
| `limit` | Integer | ❌ No | Max results (default: 50) | `20` |

**Response Structure**:
```json
{
  "patients": [
    {
      "patient_id": "12345",
      "mrn": "MRN-123456",
      "full_name": "أحمد محمد علي",
      "date_of_birth": "1985-05-15",
      "age": 39,
      "gender": "Male",
      "phone": "+966XXXXXXXXX"
    },
    {
      "patient_id": "12346",
      "mrn": "MRN-123457",
      "full_name": "أحمد محمد حسن",
      "date_of_birth": "1990-08-20",
      "age": 34,
      "gender": "Male",
      "phone": "+966YYYYYYYYY"
    }
  ],
  "total": 2
}
```

**Notes**:
- Search supports partial matching on name and phone
- MRN search is exact match (case-insensitive)
- Results limited to prevent excessive data exposure
- May require authentication and authorization

## Section C: Assumptions / Open Questions / Risks

### C.1 Assumptions

1. **Patient Identification**:
   - Patients are uniquely identified by `patient_id` (internal) and `mrn` (Medical Record Number)
   - MRN is the hospital's standard patient identifier
   - All API requests use `patient_id`, not MRN (MRN used for search only)

2. **Patient-Incident Linkage**:
   - Incidents are linked to patients via `patient_id` or `patient_name` field
   - A single incident may involve one patient (not multiple)
   - Or: Incidents reference patients by name (string match, not foreign key)

3. **Access Control**:
   - Only authorized users (doctors, quality assurance, administrators) can access patient history
   - Access may be restricted to patients in user's department
   - All access should be logged for compliance (HIPAA, local regulations)

4. **Data Anonymization**:
   - Patient names and identifiers are stored as-is (not anonymized)
   - Anonymization/masking may be applied at export or report level
   - Phone numbers and emails may be partially masked in UI

5. **History Depth**:
   - Default query returns last 100 incidents (paginated)
   - No automatic time limit (can query all-time history)
   - Very old incidents remain accessible unless archived

6. **Incident Status**:
   - All incident statuses are included (Open, Closed, etc.)
   - No filtering by default; user can apply filters
   - Closed incidents remain in patient history indefinitely

7. **Patient Profile Completeness**:
   - Not all patients have complete profiles (optional fields may be null)
   - Emergency contact and email may be missing
   - Age is computed from date of birth (not stored)

8. **Export Logging**:
   - Export actions are logged for audit trail
   - Log includes: user, patient_id, export format, timestamp
   - Exports may be subject to approval or restrictions

9. **Read-Only Page**:
   - No ability to edit patient information from this page
   - No ability to add or remove incidents
   - Changes to patient/incident data happen in other modules

10. **Multi-Language Support**:
    - Patient names primarily in Arabic
    - Department and category names available in both Arabic and English
    - UI displays both or allows language toggle

### C.2 Open Questions

1. **Patient Identification Method**:
   - Is `patient_id` an integer or string (UUID)?
   - Is MRN globally unique across the hospital system?
   - Can MRN change over time (e.g., patient re-registration)?

2. **Patient-Incident Linking Accuracy**:
   - How are patients linked to incidents? (ID reference vs name matching?)
   - If by name, how are duplicates/similar names handled?
   - Can an incident be linked to multiple patients (e.g., family complaints)?

3. **Anonymization Requirements**:
   - Should patient names be anonymized in exports?
   - Should certain fields (phone, email, address) be redacted for some users?
   - Are there different access levels (full access vs limited)?

4. **Access Control Rules**:
   - Can any authenticated user view any patient's history?
   - Or restricted by department/role?
   - Should patient consent be required for access?

5. **History Scope**:
   - Should there be a default time limit (e.g., last 5 years)?
   - Or always show full history regardless of age?
   - Are archived incidents included or excluded?

6. **Incident Description Privacy**:
   - Should full `complaint_text` be visible in list view?
   - Or truncated/summarized for privacy?
   - Should certain incident types be hidden or masked?

7. **Export Restrictions**:
   - Can any user export patient history?
   - Or restricted to certain roles (administrators, auditors)?
   - Should exports be approved before download?

8. **Performance Optimization**:
   - What is the maximum number of incidents per patient?
   - Should there be pagination by default?
   - Should older incidents be loaded on-demand (lazy loading)?

9. **Search Privacy**:
   - Should search results be limited to prevent fishing for patient data?
   - Should there be minimum search criteria (e.g., can't search all patients)?
   - Should search require specific reason/justification?

10. **Refresh Behavior**:
    - Does "Refresh" button re-fetch patient profile, incidents, or both?
    - Is there a risk of stale data if incidents are updated elsewhere?
    - Should there be auto-refresh or manual only?

11. **Empty State Handling**:
    - What if a patient has zero incidents?
    - Should there be a message indicating no history?
    - Or assume all patients have at least one incident (registration event)?

12. **Incident Details Modal**:
    - Is there a separate detail view for individual incidents?
    - Or is the table view sufficient?
    - Should users be able to navigate to full incident record?

### C.3 Risks

1. **Patient Privacy Violations**:
   - Unauthorized access to patient history is a serious compliance risk
   - Need strict role-based access control (RBAC)
   - All access must be logged and auditable

2. **Data Leakage via Export**:
   - CSV/JSON exports contain sensitive patient information
   - Exports may be shared inappropriately
   - Consider watermarking, encryption, or restricted distribution

3. **Search Abuse**:
   - Users may search for patients without legitimate reason
   - Potential for data mining or unauthorized lookups
   - Need search logging and monitoring

4. **Name Matching Errors**:
   - If incidents linked by patient name (string), errors may occur
   - Similar names may cause cross-patient contamination
   - Need validation of patient linkage

5. **Performance with High-Volume Patients**:
   - Some patients may have hundreds or thousands of incidents
   - Fetching all incidents without pagination may be slow
   - Need efficient querying and indexing

6. **Stale Data**:
   - If patient profile or incidents are updated elsewhere, this page may show outdated data
   - Need refresh mechanism or real-time updates
   - Consider caching strategy

7. **Incomplete Patient Records**:
   - Missing or incorrect patient information may cause confusion
   - Need graceful handling of null/empty fields
   - Validate data completeness before display

8. **Concurrent Access**:
   - Multiple users accessing same patient history simultaneously
   - No locking needed (read-only), but may cause version confusion
   - Consider showing "Last Updated" timestamp

9. **Export File Naming**:
   - Export filenames may contain patient names (privacy risk if file is shared)
   - Consider generic naming or patient ID only
   - Warn users about file sensitivity

10. **Department Name Consistency**:
    - If department names change over time, historical incidents may show old names
    - Need consistent naming or mapping to current structure
    - Consider displaying "at time of incident" vs "current department"

11. **Doctor Name Accuracy**:
    - If doctor name is free-text (not linked to doctor entity), may have typos or variations
    - Consider standardization or linking to doctor records
    - May need "Unknown" or "Not Recorded" handling

12. **Red Flag / Never Event Indicators**:
    - If incident is both red flag and never event, how is it displayed?
    - Need clear visual indicators (icons, colors)
    - May require separate detailed view

13. **Arabic Text Encoding**:
    - Ensure proper UTF-8 encoding for Arabic text in API responses
    - Test CSV export with Arabic characters
    - Validate that exports open correctly in Excel/tools

14. **Date/Time Zones**:
    - Incident dates may be stored in UTC or local hospital time
    - Ensure consistent date display and filtering
    - Age calculation should account for time zones

15. **No Patient Selection Validation**:
    - If `patient_id` doesn't exist, API should return 404
    - Frontend should handle gracefully (show error, allow new search)
    - Consider breadcrumb or back navigation

This comprehensive API contract design provides a complete foundation for implementing the PatientHistoryPage with appropriate privacy, security, and performance considerations.
