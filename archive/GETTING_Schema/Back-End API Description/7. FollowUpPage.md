## Section C: Assumptions / Open Questions / Risks

### C.1 Assumptions

1. **Action Source Linking**:
    
    - Actions are created from incident explanations, seasonal explanations, or investigations
    - Each action has `sourceType` and `sourceId` to trace back to origin
    - Actions can also be created manually without a source
2. **Action Lifecycle**:
    
    - Actions start as `"pending"`
    - Can be marked `"delayed"` (manually or when overdue)
    - Can be marked `"completed"` (final state)
    - Completed actions are immutable (cannot change back to pending)
3. **Status Transitions**:
    
    - `pending` → `delayed` (manual or automatic)
    - `pending` → `completed`
    - `delayed` → `pending` (when delayed again)
    - `delayed` → `completed`
    - `completed` → (no further transitions)
4. **Deletion Behavior**:
    
    - "Delete" button in UI actually marks action as completed (soft delete)
    - True deletion not supported in current implementation
    - Preserves audit trail and history
5. **Notes Management**:
    
    - Notes field is append-only (new notes added to existing)
    - Each update appends timestamp and reason
    - Full history preserved in single text field
6. **Permission Model**:
    
    - Users can view all actions across departments (filtered by access)
    - Users can update actions assigned to their department
    - Some operations may require elevated permissions
7. **Calendar View**:
    
    - Actions displayed on calendar by `dueDate`
    - Color-coded by status/priority
    - Only pending/delayed actions shown by default
8. **Time-based Grouping**:
    
    - Overdue: `dueDate < today && status === "pending"`
    - Next 7 days: `today <= dueDate <= today+7 && status === "pending"`
    - Next 8-14 days: `today+8 <= dueDate <= today+14 && status === "pending"`
    - Groups are mutually exclusive
9. **LocalStorage Integration**:
    
    - Current implementation uses localStorage for demo purposes
    - Actions created from feedback forms stored temporarily
    - Production should use database backend only
10. **Audit Trail**:
    
    - Backend tracks `createdAt`, `createdBy`, `lastUpdatedAt`, `lastUpdatedBy`
    - Frontend does not send these fields
    - Full change history may be tracked separately

### C.2 Open Questions

1. **Action Immutability**:
    
    - Can completed actions be edited or reopened?
    - What if an action was marked complete by mistake?
    - Should there be an "undo" or "reopen" feature?
2. **Delete vs Complete**:
    
    - Should "delete" truly delete or mark as complete?
    - Current code marks as complete - is this intended?
    - Should there be separate "Complete" and "Cancel/Close" actions?
3. **Automatic Status Transitions**:
    
    - Should actions automatically become `"delayed"` when overdue?
    - Or is `"delayed"` only set manually?
    - What triggers the transition from `"pending"` to `"delayed"`?
4. **Update History**:
    
    - Is update history tracked in backend?
    - Should the UI show a detailed change log?
    - Or is the `notes` field sufficient?
5. **Multi-Department Actions**:
    
    - Can an action involve multiple departments?
    - If so, how is ownership/responsibility determined?
    - Can actions be reassigned across departments?
6. **Notification System**:
    
    - Are assignees notified when actions are assigned/updated?
    - Are there reminders for upcoming or overdue actions?
    - How are notifications managed?
7. **Action Dependencies**:
    
    - Can actions have dependencies (action B requires action A)?
    - Or are all actions independent?
    - Should there be task sequences?
8. **Completion Validation**:
    
    - Does marking complete require evidence or notes?
    - Or can actions be marked complete without justification?
    - Should there be approval workflow for completion?
9. **Reassignment**:
    
    - Can actions be reassigned to different people?
    - Does reassignment require approval?
    - Is reassignment history tracked?
10. **Department Filter Data**:
    
    - How is the department list populated?
    - Should it come from a reference data endpoint?
    - Or derived from existing actions?
11. **Date Range Defaults**:
    
    - What is the default date range for fetching actions?
    - Should it be configurable (last 30 days, 90 days, all time)?
    - How far into the future should actions be fetched?
12. **Priority Escalation**:
    
    - Do priorities auto-escalate as due dates approach?
    - Or are priorities static until manually changed?
    - Should there be automatic priority rules?

### C.3 Risks

1. **Concurrent Updates**:
    
    - Multiple users may update the same action simultaneously
    - Need optimistic locking or conflict detection
    - Last write wins may cause data loss
2. **Incomplete Actions Lost**:
    
    - If "delete" marks as complete, incomplete work may be lost
    - Users may accidentally close important actions
    - Need confirmation or undo mechanism
3. **Note Field Overflow**:
    
    - Append-only notes field may grow very large
    - Could impact performance or display
    - Consider structured update history instead
4. **No Action Templates**:
    
    - Recurring actions must be created manually each time
    - No support for action templates or recurring tasks
    - May lead to inconsistent action creation
5. **Missing Due Date Validation**:
    
    - Due dates can be set to past dates
    - Or unrealistic future dates (e.g., year 2100)
    - Backend should validate date ranges
6. **Status Consistency**:
    
    - If action is overdue but status is "pending", inconsistent state
    - Need clear definition of "delayed" vs overdue "pending"
    - Consider auto-updating status based on date
7. **Orphaned Actions**:
    
    - If source incident/explanation is deleted, action becomes orphaned
    - Should actions have cascade delete or remain independent?
    - How to handle broken source references?
8. **Performance with Many Actions**:
    
    - Fetching all actions without pagination may be slow
    - Filtering on frontend inefficient with large datasets
    - Consider server-side filtering and pagination
9. **Time Zone Issues**:
    
    - Due date comparisons depend on time zones
    - Server and client may be in different time zones
    - Need consistent date handling (UTC or local hospital time)
10. **Action Ownership Ambiguity**:
    
    - If assignee leaves or changes roles, who owns the action?
    - Need mechanism for reassignment or escalation
    - Consider backup assignees or role-based assignment
11. **Completion Date Backdating**:
    
    - Users may set completion date in the past
    - Could be legitimate (forgot to mark) or abuse
    - Need validation or audit trail
12. **No Evidence Tracking**:
    
    - Actions marked complete without evidence or proof
    - No attachment or documentation support
    - May need to link to evidence files or reports
13. **Statistics Consistency**:
    
    - Statistics computed on frontend may be inconsistent with backend
    - If filters applied, stats may not match reality
    - Consider including stats in API response
14. **LocalStorage Sync Issues**:
    
    - Current implementation uses localStorage for demo
    - Multiple tabs may have inconsistent state
    - Real implementation should use database only
15. **Calendar View Scalability**:
    
    - Many actions on same day may clutter calendar
    - Need grouping or summary view for busy days
    - Consider month/week/day view options
