## Section C: Assumptions / Open Questions / Risks

### C.1 Assumptions

1. **Authentication & Authorization**:
    
    - Users are authenticated and their department/section is known
    - Only authorized department staff can submit explanations for their own department's incidents
    - May require role-based access control (RBAC)
2. **Incident Record Status**:
    
    - Incidents start as OPEN
    - Become OVERDUE when `daysSinceReceived > delay_threshold_days`
    - Change to CLOSED only when explanation is submitted via `/close` endpoint
    - Forcibly closed incidents (mentioned in other pages) are NOT shown in this list
3. **Delay Threshold**:
    
    - Configured globally in settings (default: 14 days)
    - Applied uniformly across all departments
    - May be configurable per department or severity level in future
4. **Seasonal Violations**:
    
    - Pre-computed by a separate process (e.g., nightly batch job)
    - Only violations (where actual > threshold) are shown
    - Violations are generated per season, per department, per metric
    - Seasons are defined as quarters (Q1, Q2, Q3, Q4)
5. **Follow-Up Integration**:
    
    - `action_items` from both incident and seasonal explanations are synced to a Follow-Up system
    - The Follow-Up system is separate but linked (may have its own API)
    - Action items are created as new records in the Follow-Up system, linked to the original explanation
6. **Patient Privacy**:
    
    - Patient names shown are sufficient for department identification
    - No medical details or sensitive patient data are exposed beyond complaint description
    - Complies with hospital data privacy policies
7. **Explanation Editability**:
    
    - Current implementation suggests explanations are write-once
    - No UI for editing or viewing previously submitted explanations
    - May require audit trail if editing is allowed
8. **Multi-language Support**:
    
    - UI supports both Arabic and English
    - Data fields contain both Arabic (qism, classification) and English (department, metric labels)
    - Explanations likely submitted in Arabic

### C.2 Open Questions

1. **Incident Record Ownership**:
    
    - Can multiple departments provide explanations for the same incident?
    - If `targetDepartment` is the responsible department, can other departments view or comment?
    - What happens if the responsible department changes?
2. **Explanation Versioning**:
    
    - Can departments revise their explanations after initial submission?
    - Is there an approval workflow for explanations?
    - Are explanations reviewed or audited by quality assurance teams?
3. **Status Transitions**:
    
    - Can a CLOSED record be reopened?
    - What is the difference between "Save" and "Save & Close"?
    - Are there other statuses beyond OPEN, OVERDUE, CLOSED?
4. **Seasonal Violation Computation**:
    
    - How are seasonal thresholds defined (per department, per metric)?
    - Who configures these thresholds?
    - Are thresholds static or adjusted over time?
    - How is "HCAT_violations" percentage calculated?
5. **Follow-Up Action Lifecycle**:
    
    - How are follow-up actions tracked after creation?
    - Can departments update action item status?
    - Is there a notification or reminder system for overdue actions?
6. **Filters and Pagination**:
    
    - Should filters be applied server-side or client-side?
    - Is pagination needed for large result sets?
    - What is the expected maximum number of open records per department?
7. **Department Hierarchy**:
    
    - Are departments organized hierarchically (like Dashboard: Idara > Dayra > Qism)?
    - Can explanations be submitted at different levels?
    - Can a parent department view child department explanations?
8. **Red Flags**:
    
    - Are red flag incidents treated differently in the explanation process?
    - Do they have stricter deadlines or additional required fields?
    - Are they escalated to higher authorities?
9. **Notifications**:
    
    - Are departments notified when records become OVERDUE?
    - Are there reminders for pending seasonal explanations?
    - Who receives notifications?
10. **Data Completeness**:
    
    - Are all fields in the mock data always present?
    - What happens if `immediateAction` is null/empty?
    - Are some fields optional in the database?

### C.3 Risks

1. **Performance with Large Datasets**:
    
    - Fetching all open records without pagination could be slow
    - Client-side filtering may not scale well
    - Consider server-side filtering and pagination
2. **Concurrent Explanation Submission**:
    
    - What if two users from the same department submit explanations for the same incident simultaneously?
    - Need optimistic locking or conflict resolution
3. **Stale Data**:
    
    - `daysSinceReceived` is computed dynamically; may become stale if page isn't refreshed
    - Need refresh mechanism or real-time updates
4. **Follow-Up System Dependency**:
    
    - If Follow-Up system is unavailable, should explanation submission fail?
    - Consider async processing or eventual consistency
5. **Incomplete Explanations**:
    
    - Required fields enforced client-side only
    - Backend must validate required fields to prevent partial submissions
6. **Department Identification**:
    
    - If user authentication doesn't provide department context, how is `targetDepartment` filter applied?
    - May need user profile endpoint
7. **Seasonal Threshold Configuration**:
    
    - If thresholds are misconfigured, violations may be incorrectly identified
    - Need admin UI for threshold management
8. **Action Item Duplication**:
    
    - If same explanation is submitted multiple times (due to error), action items may be duplicated in Follow-Up system
    - Need idempotency checks
9. **No Audit Trail**:
    
    - Current UI doesn't show who submitted explanation or when
    - May need audit metadata in API responses
10. **Arabic Text Encoding**:
    
    - Ensure proper UTF-8 encoding for Arabic text in API requests/responses
    - Validate RTL (right-to-left) text handling
11. **Date/Time Zones**:
    
    - Server and client may be in different time zones
    - Ensure consistent date calculations for `daysSinceReceived`
    - Use ISO 8601 datetime format consistently
12. **Seasonal Explanation Deadline**:
    
    - No visible deadline for submitting seasonal explanations
    - May need deadline enforcement or reminder system
