## Section C: Assumptions, Open Questions, and Risks

### C1. Assumptions

#### Time Range and Aggregation
1. **Default Time Window**: System defaults to last 12 calendar months when no `start_date`/`end_date` specified.
2. **Calendar Month**: Aggregation uses calendar month boundaries (1st to last day), not rolling 30-day windows.
3. **Month Granularity**: Minimum aggregation unit is one month; no weekly or daily trends in Iteration 1.
4. **Complete Months Only**: Partial months (e.g., current incomplete month) are either excluded or clearly marked.
5. **Maximum Time Range**: System allows maximum 36 months (3 years) of historical data to prevent performance degradation.

#### Data Completeness
6. **Zero-Incident Months Included**: By default, months with zero incidents are included in `monthly_data` arrays (incident_count=0) to ensure continuous timeline for charts.
7. **Inactive Domains/Categories Excluded**: Domains or categories with zero incidents across entire time range are excluded by default (unless `include_inactive=true`).
8. **No Data Gaps**: System ensures every month in range appears in response, even if count is zero.

#### Calculation Logic
9. **Trend Direction Rules**:
   - **Increasing**: First month count < last month count by >10%
   - **Decreasing**: First month count > last month count by >10%
   - **Stable**: Change between first and last month is ≤10%
10. **Trend Percentage**: Calculated as `((last_month - first_month) / first_month) × 100`
11. **Month-over-Month Change**: Calculated as `current_month - previous_month` (null for first month)
12. **Percentage of Total**: Calculated as `(domain_count / all_incidents_for_month) × 100`

#### Data Scope
13. **All Incidents Included**: Trends include all incident statuses (open, closed, in_progress) unless business rules dictate otherwise.
14. **Received Date Used**: Aggregation based on `received_date` (when complaint was logged), not `incident_date` (when incident occurred).
15. **No Department Filtering**: Trends are hospital-wide; no department-level filtering in Iteration 1.
16. **No Severity Filtering**: Trends include all severity levels; no filtering by red flags or Never Events.

#### Technical Constraints
17. **Pre-Aggregated Data**: Trend data is pre-aggregated monthly (not calculated on-demand from raw incidents) for performance.
18. **Server-Side Trend Calculation**: All derived fields (`trend_direction`, `trend_percentage`, `month_over_month_change`) calculated server-side.
19. **Chart/Table Reuse**: Both chart and table components consume same API endpoint; no separate endpoints for visualization vs tabular data.
20. **Caching**: Trend data is cached for 1 hour; changes to incidents within past hour may not reflect immediately.

### C2. Open Questions

#### Time Range and Granularity
1. **Default Time Window**: Is 12 months the correct default, or should it be configurable (6, 12, 24 months)?
2. **Current Month Inclusion**: Should incomplete current month be included in trends, excluded, or marked as "preliminary"?
3. **Historical Data Limit**: What is oldest available data? Should system prevent queries beyond available history?
4. **Future Months**: Should system return future months (with zero counts) for chart continuity, or stop at current month?

#### Aggregation Rules
5. **Date Basis**: Should aggregation use `received_date` (when logged) or `incident_date` (when occurred)? Current assumption is `received_date`.
6. **Backdated Incidents**: If incident is logged today but incident_date is 3 months ago, which month does it count toward?
7. **Timezone Handling**: For hospitals spanning multiple time zones, which timezone determines month boundaries?

#### Trend Calculation
8. **Trend Direction Threshold**: Is 10% the correct threshold for stable vs increasing/decreasing? Should it be configurable?
9. **Trend Algorithm**: Should trend use linear regression (slope), simple first-to-last comparison, or moving average?
10. **Seasonality Adjustment**: Should trends account for known seasonal patterns (e.g., flu season, holiday staffing)?
11. **Outlier Handling**: If one month has abnormally high count (data entry backlog, outbreak), should it be flagged or smoothed?

#### Domain and Category Scope
12. **Inactive Taxonomy**: If a domain or category is deactivated in SettingPage mid-timerange, how are historical counts handled?
13. **Taxonomy Changes**: If category is moved from one domain to another, do historical counts follow the new structure or preserve old structure?
14. **New Domains/Categories**: If new domain is created mid-timerange, should it show zero for all prior months, or be excluded until first incident?

#### Data Filtering (Future Consideration)
15. **Department Filtering**: Should trends support filtering by department (even if not in UI for Iteration 1)?
16. **Severity Filtering**: Should trends support showing only high-severity or red-flag incidents?
17. **Status Filtering**: Should trends distinguish between open vs closed incidents, or always show total?

#### Performance and Scalability
18. **Maximum Categories**: If hospital has 200+ categories, should
