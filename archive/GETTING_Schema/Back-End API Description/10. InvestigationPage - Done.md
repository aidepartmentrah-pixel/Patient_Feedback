## Section A: Data Needs

### A.1 Investigation Query Parameters (Input Filters)

| Field               | Type           | Required | Description                                                |
| ------------------- | -------------- | -------- | ---------------------------------------------------------- |
| `season`            | String         | ✅ Yes    | Season/period identifier (e.g., "2024-Q4", "2024-Oct-Dec") |
| `administration_id` | Integer/String | ❌ No     | Filter by specific administration (Idara)                  |
| `department_id`     | Integer/String | ❌ No     | Filter by specific department (Dayra)                      |
| `section_id`        | Integer/String | ❌ No     | Filter by specific section (Qism)                          |
| `tree_type`         | Enum           | ✅ Yes    | Visualization/aggregation type                             |

**Tree Type Values**:

- `"incident_count"` - Total incident count per node
- `"domain_distribution_numbers"` - Domain breakdown (absolute counts)
- `"domain_distribution_percentage"` - Domain breakdown (percentages)
- `"severity_distribution_numbers"` - Severity breakdown (absolute counts)
- `"severity_distribution_percentage"` - Severity breakdown (percentages)
- `"red_flag_incidents"` - Red flag incident count per node
- `"never_event_incidents"` - Never event incident count per node

**Note**: Organizational filters form a hierarchy. If `section_id` is provided, its parent `department_id` and grandparent `administration_id` are implied.

## Section C: Assumptions / Open Questions / Risks

### C.1 Assumptions

1. **Season Definition**:
    
    - Seasons are predefined, calendar-based periods (typically quarters)
    - Seasons do not overlap
    - Current season is the most recent complete period
    - Seasons are defined in backend configuration or database
2. **Organizational Hierarchy**:
    
    - Three-level hierarchy: Administration → Department → Section
    - Fixed depth (no variable depth)
    - Each node belongs to exactly one parent
    - Organizational structure is relatively stable within a season
3. **Aggregation Scope**:
    
    - When filtering by department, tree shows only that department and its child sections
    - When filtering by administration, tree shows that administration, its departments, and their sections
    - No filtering shows entire hospital hierarchy (all administrations)
4. **Incident Attribution**:
    
    - Each incident is attributed to exactly one section (lowest level)
    - Incidents roll up to parent department and administration
    - No cross-organizational incidents (or attributed to primary section)
5. **Percentage Calculations**:
    
    - For distribution percentages, each node sums to 100%
    - Percentages are calculated backend (not frontend)
    - Domain/severity breakdowns are mutually exclusive (no overlap)
6. **Red Flags and Never Events**:
    
    - Red flags and never events are boolean flags on incident records
    - An incident can be both red flag and never event
    - Counts are distinct (one incident counted once per flag)
7. **Tree Visualization Handling**:
    
    - Frontend renders the tree structure
    - Backend only provides aggregated data
    - No visualization-specific logic in backend
8. **Empty Nodes**:
    
    - Nodes with zero incidents are included in the tree (value = 0)
    - Empty nodes help show organizational structure
    - Or: Nodes with zero incidents are omitted (more compact tree)
9. **Data Freshness**:
    
    - Investigation data is pre-aggregated or cached
    - Not real-time (acceptable lag for completed seasons)
    - Current season data may update periodically
10. **Access Control**:
    
    - Users can investigate any organizational scope
    - Or: Users can only investigate their own department/administration
    - No row-level security in API (handled at UI layer or auth layer)

### C.2 Open Questions

1. **Season Granularity**:
    
    - Are seasons always quarterly? Or can they be monthly, yearly, custom?
    - Can users define custom date ranges instead of predefined seasons?
    - How far back in history can users investigate?
2. **Percentage Calculation Method**:
    
    - For domain/severity distributions, are percentages of:
        - Total incidents in that node?
        - Total incidents in the entire hospital?
        - Total incidents in the selected scope?
    - Should percentages be rounded or precise (e.g., 33.33% vs 33%)?
3. **Zero-Incident Nodes**:
    
    - Should nodes with zero incidents be included in the tree?
    - Or only nodes with at least one incident?
    - How does this affect tree rendering and visual emphasis?
4. **Nested Filtering**:
    
    - If user selects a section, should the tree show:
        - Only that section (single node)?
        - That section's parent department and siblings?
        - Full hierarchy with emphasis on selected section?
5. **Red Flag / Never Event Definitions**:
    
    - How are red flags identified? (Manual flag, severity-based, category-based?)
    - How are never events defined? (Specific categories, classifications?)
    - Are these definitions configurable or hardcoded?
6. **Domain and Severity Values**:
    
    - What are the exact domain values? (["clinical"](vscode-file://vscode-app/c:/Users/IT/AppData/Local/Programs/Microsoft%20VS%20Code/resources/app/out/vs/code/electron-browser/workbench/workbench.html), ["management"](vscode-file://vscode-app/c:/Users/IT/AppData/Local/Programs/Microsoft%20VS%20Code/resources/app/out/vs/code/electron-browser/workbench/workbench.html), ["relational"](vscode-file://vscode-app/c:/Users/IT/AppData/Local/Programs/Microsoft%20VS%20Code/resources/app/out/vs/code/electron-browser/workbench/workbench.html) confirmed?)
    - What are the exact severity values? (["high"](vscode-file://vscode-app/c:/Users/IT/AppData/Local/Programs/Microsoft%20VS%20Code/resources/app/out/vs/code/electron-browser/workbench/workbench.html), ["medium"](vscode-file://vscode-app/c:/Users/IT/AppData/Local/Programs/Microsoft%20VS%20Code/resources/app/out/vs/code/electron-browser/workbench/workbench.html), ["low"](vscode-file://vscode-app/c:/Users/IT/AppData/Local/Programs/Microsoft%20VS%20Code/resources/app/out/vs/code/electron-browser/workbench/workbench.html) confirmed?)
    - Are these standardized or customizable?
7. **Multiple Tree Types Simultaneously**:
    
    - Can users view multiple tree types at once (side-by-side comparison)?
    - Or only one tree type at a time?
    - Should there be a combined/multi-metric view?
8. **Performance Optimization**:
    
    - For large hospitals with many sections, how many nodes are expected?
    - Should there be pagination or limiting of tree depth?
    - Should aggregation be pre-computed or computed on-demand?
9. **Threshold Highlighting**:
    
    - Should the API include threshold data (e.g., "this node exceeded threshold")?
    - Or is threshold logic handled separately (from seasonal explanations)?
    - Should nodes that triggered violations be flagged in the response?
10. **Historical Comparison**:
    
    - Can users compare multiple seasons side-by-side?
    - Should the API support multi-season queries?
    - Or are investigations always single-season?
11. **Drill-Down Capability**:
    
    - If user clicks a node, should it fetch more detailed data?
    - Or does the initial tree include all levels always?
    - Is there a separate endpoint for node details?
12. **Export Functionality**:
    
    - Can investigation trees be exported (CSV, PDF)?
    - Should the API provide export-friendly data format?
    - Or is export handled entirely client-side?

### C.3 Risks

1. **Large Dataset Performance**:
    
    - For hospitals with hundreds of sections, tree could be very large
    - Aggregation queries may be slow without proper indexing
    - Consider caching or pre-aggregation for completed seasons
2. **Inconsistent Organizational Structure**:
    
    - If organizational structure changes mid-season, aggregations may be inconsistent
    - Historical incidents may reference departments/sections that no longer exist
    - Need strategy for handling renamed/merged/split units
3. **Percentage Rounding Errors**:
    
    - Domain/severity percentages may not sum exactly to 100% due to rounding
    - Frontend may show 99.9% or 100.1% instead of 100%
    - Consider using fixed precision or forcing sum to 100%
4. **Empty Tree Scenarios**:
    
    - If a season has zero incidents, tree will be empty or all zeros
    - Need graceful handling in UI (empty state message)
    - Consider excluding seasons with insufficient data
5. **Slow Aggregation Queries**:
    
    - Computing percentages and breakdowns on-the-fly may be slow
    - Especially for hospital-wide queries across thousands of incidents
    - Strongly recommend pre-aggregation for completed seasons
6. **Red Flag / Never Event Ambiguity**:
    
    - If definitions are unclear or change over time, counts may be inconsistent
    - Users may question why certain incidents are/aren't flagged
    - Need clear documentation of criteria
7. **Hierarchy Depth Variations**:
    
    - Some departments may have sections, others may not
    - Tree structure may be unbalanced (different leaf depths)
    - Frontend must handle variable-depth trees
8. **Scope Filter Confusion**:
    
    - Users may not understand difference between filtering and drilling down
    - Filtering by section may show unexpected tree structure
    - Need clear UI indicators of current scope
9. **Domain/Severity Data Quality**:
    
    - If incidents have missing or invalid domain/severity values, aggregations will be incomplete
    - Need handling of null/unknown categories
    - Consider "Other" or "Unclassified" buckets
10. **Season Boundary Edge Cases**:
    
    - Incidents on season boundary dates (e.g., last day of quarter) may be misattributed
    - Need clear definition of inclusive/exclusive date ranges
    - Time zone issues if date-only comparisons are used
11. **Tree Type Validation**:
    
    - If invalid `tree_type` parameter is sent, API should return clear error
    - Consider enum validation and meaningful error messages
    - Document all valid tree type values
12. **Real-Time vs Static Data**:
    
    - For current/ongoing seasons, data may change as new incidents are reported
    - Users may see different results on refresh
    - Consider showing "Last Updated" timestamp
13. **No Raw Incident Access**:
    
    - Investigation page shows only aggregates, not individual incidents
    - Users cannot drill down to see which specific incidents contributed to a node
    - May need separate "View Details" feature linking to raw incident list
14. **Cross-Department Incidents**:
    
    - If an incident involves multiple departments, which node does it count toward?
    - Need clear attribution rule (primary/issuing department vs target department)
    - May lead to confusion if attribution logic is unclear
15. **Memory Constraints**:
    
    - Very large tree structures (deep JSON) may cause memory issues on client
    - Consider streaming or chunked responses
    - Or limit tree depth/breadth in query parameters
